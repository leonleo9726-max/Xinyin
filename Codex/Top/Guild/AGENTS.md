# Guild 公会模块执行规则

> 本文件定义 Guild 模块的执行约束；业务口径以 [`核心业务规则.md`](./核心业务规则.md) 为准。

---

## 1. 工作目录与资料

### 1.1 目录边界

- 当前工作目录必须在 `E:\Codex\Top\Guild` 或其子目录。
- 严禁读取、搜索或引用同级 `Wechill` 目录。

## 2. 薪资与展示口径

### 2.1 查询前置规则

- 执行任何公会薪资、薪资余额、预支抵扣、提现余额或结算数据查询前，必须完整读取本文件及 `核心业务规则.md`；不得仅凭历史记忆、字段名称或既往查询结果推断业务口径。
- 查询结果必须严格按 `核心业务规则.md` 中对应的客户端或后台公式、数据源和结算状态输出。字段含义、汇总范围或金币工资归属不一致时，先列出“异常声明”并核验快照或明细，不得自行补算、重复累加或省略金额。
- 用户明确要求通过 XXJob 结算指定公会月份时，使用 `$guild-monthly-settlement` 并遵循 `核心业务规则.md` §6.1。首次请求只做预检并列出完整执行参数；必须在后续消息得到用户明确确认后，重新核验并提交任务。薪资查询不得触发结算。

### 2.2 薪资计算

- `policy_type=1` 为 TG 政策（月结，原普通政策），`policy_type=2` 为自由政策（月结），`policy_type=3` 为自由政策（周结）；`policy_type=3` 是合法政策，不得判定为异常。
- 自由政策月结保持现有标准：总分成比 `1.1`、钻石换算美元比例 `150000`、主播分成比 `0.8`、公会长分成比 `0.2`、强制充值比例 `0.2`。月结按自然月计算；主播使用当月 `D_balance`，公会长使用当月 `D_flow`。
- 自由政策周结使用独立新标准：总分成比 `0.8`、钻石换算美元比例 `130000`、主播分成比 `0.73`、公会长分成比 `0.27`、强制充值比例 `0.2`；周结工资拆分为金币 `0%`、非金币 `100%`。周结按 UTC+3 自然周计算，主播使用当周 `D_balance`，公会长使用当周 `D_flow`。
- 普通政策主播侧 `X/Z` 使用当期实际值 `actual_diamond_amount` 命中档位和计算超档；公会长侧 `Y` 保持按有效钻石流水计算。`valid_diamond_balance_amount` 仍是独立余额展示字段，不得替代普通政策主播实际值；自由政策月结/周结继续使用对应周期的 `D_balance`。
- 自由政策周结实时明细读取 `guild.guild_salary_detail_weekly`，结算快照读取 `guild.guild_settlement_bill_weekly`；周结参数不得沿用月结的 `1.1 / 150000 / 0.8 / 0.2`。
- 普通政策：先命中档位和超档，再按 X/Y/Z 拆分；完整超档步数为 `FLOOR(MAX(0, 实际值-档位目标值)/超档步长)`，超档增量等于完整步数乘单步超档金额，不足一个完整步长按 `0` 处理。
- 普通政策存在 34、35 档，两档金币工资比例固定为 `5%`。实时工资和新生成结算必须写入该比例；已结算历史仍读取原结算快照，比例不一致时先列出“异常声明”，不得用当前规则覆盖历史结果。
- 新主播在当前成员关系 `guild_member.joined_at` 所在自然月享受新手保护，不适用有效天未达标扣减。保护期结束后，普通政策有效天未达标时，主播底薪、TG 奖励和对应公会长分成各按 `85%` 结算，再拆分金币工资和非金币工资。
- 每个工资项必须先拆分金币工资和非金币工资，再汇总角色工资。禁止先汇总总工资后统一拆分。
- 金币工资只能提现金币，不能现金提现、提现给公会长、计入可预支金额或用于预支抵扣。

### 2.3 端侧统计

- 客户端主播总薪资与薪资余额均包含金币工资。
- 客户端公会长总薪资仅指管理收益，不含本人自播薪资。
- 后台主播薪资页和后台公会薪资页的公会长总薪资均只包含管理收益；公会长本人自播工资只计入主播总薪资一次。
- 客户端公会总薪资为主播总薪资加公会长管理收益；不得重复加入已包含在主播总薪资中的公会长自播薪资。
- 查询结果必须声明客户端或后台口径。自由政策没有普通政策底薪/TG 分项时，客户端展示 `--`，不得以总薪资替代。
- 月结明细与周结明细必须按周期和政策类型隔离；`policy_type=3` 不得写入或读取月结表，月结明细查询只读取 `policy_type=1/2`。
- 成员展示按有效成员当前政策分类：`policy_type=1/2` 归入“月结成员”，`policy_type=3` 归入“周结成员”；分类依据是成员关系政策，不以是否已有工资明细为条件。
- 分类展示必须覆盖全部有效成员；公会长兼主播保留公会长角色并按其主播政策进入对应分组。没有对应工资行时保留成员并标记“暂无工资明细”，不得从分组中删除。
- 来源状态必须绑定到工资明细逐行展示；同一成员同时存在历史结算快照和当前实时行时，分别列出对应周期、来源和结算状态，不得合并成“历史快照+当前实时”等单一来源状态。成员汇总只能引用各条来源明细，不能用拼接状态替代逐行来源。
- 公会汇总必须同步按周期拆分：分别展示月结主播薪资、月结公会长管理收益、月结公会薪资，以及周结主播薪资、周结公会长管理收益、周结公会薪资；最后再给出本月合计。本月累计中的周结汇总只计入未结算周结行；单独查询历史周时按所选周结快照汇总该周结果。不得把已结算周结快照计入本月累计，也不得只展示混合后的公会总额。
- 月结和周结主播明细均需逐主播展示对应的公会长管理收益、主播底薪和主播 TG 薪资；`policy_type=1` 展示实际底薪/TG 金额，`policy_type=2/3` 为自由政策，对应底薪/TG 字段展示 `--`，不得用主播总薪资替代。
- 当月公会总薪资按自然月累计时，先分别读取月结成员的 `guild_salary_detail`/`guild_settlement_bill` 与当月周结成员的 `guild_salary_detail_weekly`/`guild_settlement_bill_weekly`，再汇总主播工资和公会长管理收益；月结行按原口径计入，周结仅将未结算行计入汇总，已结算周结快照仅作明细展示；周结金额不得写入月结表或伪装成月结明细。

### 2.4 后台薪资查询

- 后台主播薪资和公会薪资查询必须选定实时数据或结算快照之一；汇总、列表、详情和导出使用相同筛选条件、周期、数据源、快照版本及权限范围，不得拼接两类来源。
- 页面中的可提现余额（含金币）始终读取当前余额池，不从所选周期工资推导；历史页面也展示当前实时余额，无法明确归因公会的余额不计入公会汇总。
- 查询、排序、详情和导出均为只读操作，不触发结算、快照、工资入账或余额变更。导出覆盖完整筛选结果并记录导出人、时间、筛选条件和快照版本。

## 3. 结算、成员与资金约束

### 3.1 结算与成员关系

- 历史结算读取结算快照；当前月份读取实时工资预计算行。不可用当前政策重算历史快照。
- 结算完成后保留钻石余额结算快照，不清零快照；通过结算周期、成员关系和快照唯一性防止重复结算。
- 离会或移除必须先走离会结算主链；旧成员关系及其快照保留为历史归属，新公会只结算离会后产生的流水。

### 3.2 资金与幂等

- 预支债务始终挂预支人本人；预支给他人时，月结抵扣预支人的非金币工资，不抵扣收款人工资。
- 提现提交冻结申请金额，拒绝释放冻结，通过才进入扣减和打款。所有终态审核、入账、回调和结算必须幂等。

## 4. 数据查询与变更

- 默认查询使用 `.env` 中 `APP_ENV=test` 的测试库。经明确授权的生产薪资查询只能通过
  `query_guild_salary.py --environment production --confirm-production` 执行，且必须使用
  `PROD_MYSQL_*` 独立凭据、`PROD_MYSQL_READ_ONLY=true` 和只读事务；不得将生产结果表述为测试数据。
- `guild-salary-query` 仅允许只读薪资查询；生产提现、预支、结算、余额或其他写操作一律拒绝。测试环境月结仅按 `$guild-monthly-settlement` 的预检和二次确认流程触发。
- 首次查询表必须执行 `SHOW COLUMNS FROM <表名>`，不得使用 `DESC`。单个任务连续执行 3 次及以上 MySQL 查询时，写 Python 脚本用 `mysql.connector` 一次完成。
- 用户输入的纯数字默认按 `user_no` 处理；先通过 `app.ln_user.user_no` 映射 `user_id`，仅当用户明确说明为 `user_id` 时例外。
- 用户明确输入“公会 ID”或“公会编号”时，默认按 `guild.guild_info.guild_no` 查询；仅当用户明确说明为数据库主键时，才按 `guild.guild_info.id` 查询。
- 查询工资时使用 `guild_salary_detail.bill_owner_type=1` 取得主播侧，用 `guild_settlement_bill` 和 `settlement_bill_id` 区分已结算快照与实时未结算工资。不要将仅有实时行的数据误称已结算。
- 查询或解释普通政策主播工资时，读取并展示 `actual_diamond_amount`、档位目标、超档增量及薪资基数；档位和超档按 `actual_diamond_amount` 计算。`valid_diamond_balance_amount` 是独立余额字段，不能替代实际值。自由政策主播侧仍按对应周期的有效钻石余额计算，公会长管理收益保持有效钻石流水口径。
- 用户要求修正或迁移未结算实时工资月份时，不能只改 `guild_salary_detail.settlement_month`；必须按 `核心业务规则.md` 同步迁移/修正对应的底层周期收入汇总及关联兑钻数据，并校验成员归属、源/目标周期汇总和重复/缺失。已结算账单与快照不得直接改月份或迁移。
- 查询周结工资时使用 `guild_salary_detail_weekly` / `guild_settlement_bill_weekly`，以 `period_start` 标识 UTC+3 自然周；`settlement_bill_id=0` 表示周结实时行，不能与月结表混查。
- `guild_salary_detail.bill_owner_type=2` 的 `member_id=0` 为公会汇总行，不能与按成员的公会长收益行重复相加。
- `guild_salary_detail_weekly.bill_owner_type=2` 的 `member_id=0` 同样为周结公会汇总行，不能与成员明细重复相加。
- 兑换钻石流水只汇总已确认兑换记录，不使用有效钻石流水与有效钻石余额的差额推算，也不将兑钻数据作为工资基数。
- 读取结构化数据后检查字段和前 3 行；遇到空值、负数钻石或薪资、重复记录或快照、快照缺失或版本不一致、归属缺失、异常状态或汇总遗漏金币工资时，先列出“异常声明”，不得按当前数据补算历史结果。
- 薪资查询对外结果默认不展示成员关系 ID（`member_id`）；内部可使用该字段进行成员关联、去重和审计核对。
- 后台查询、详情和导出必须分别校验权限及授权公会范围；无权限或越权请求不得返回薪资金额。

## 5. 文档维护

- 改动薪资、成员关系、提现、预支、结算、状态机或政策规则时，同步更新 `核心业务规则.md`、PRD 和测试用例。
- 改动 `/api/guild/**` 时，同步更新客户端接口合同；改动 `/guild/**` 或 `/internal/guild/**` 时，同步更新 CMS 接口合同与调用流程。
- 发现表、字段、枚举、日志路径或结算口径后，更新 `E:\Codex\Top\数据库表结构.md` 或本目录文档。
- 输出使用简体中文；金额、统计口径、数据源和结算状态需明确；账号、密钥、token、连接串默认脱敏。
