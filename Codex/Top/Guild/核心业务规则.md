# TALO 公会模块核心业务规则

> 本文件是公会成员、薪资、余额池、提现、预支、月结、周结和后台薪资查询的摘要事实来源。
> 月结与周结必须按独立周期、独立明细表和独立结算账单读取；已结算历史以对应结算快照为准，进行中周期以对应实时工资预计算为准。

---

## 1. 文档范围与术语

本文件定义公会成员、薪资、余额池、提现、预支、结算及后台薪资查询的核心口径。

| 术语 | 定义 |
| --- | --- |
| 月结主播侧工资 | `guild_salary_detail.bill_owner_type=1` 的主播工资结果 |
| 周结主播侧工资 | `guild_salary_detail_weekly.bill_owner_type=1` 的主播工资结果 |
| 公会长管理收益 | 每名成员贡献的公会长侧分成汇总，不含公会长本人自播的主播侧工资 |
| 公会长自播薪资 | 公会长本人同时作为主播产生的主播侧工资 |
| 结算快照 | 已结算周期的流水、政策、工资项、扣减、预支和余额池结果 |
| 月结实时工资 | 未生成月结单时，`guild_salary_detail` 中的当前月预计算工资结果 |
| 周结实时工资 | 未生成周结单时，`guild_salary_detail_weekly` 中的当前周预计算工资结果 |
| 周结周期 | UTC+3 自然周，周一 00:00（含）至下周一 00:00（不含） |
| 可提现余额（含金币） | 当前各余额池中仍满足对应提现条件的实时可用金额；独立于所选周期工资 |

## 2. 成员关系与结算归属

### 2.1 角色与成员状态

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `role_type` | `1` | 主播 |
| `role_type` | `2` | 公会长 |
| `member_status` | `1` | 已通过，待生效 |
| `member_status` | `2` | 有效绑定 |
| `member_status` | `3` | 主播主动退出 |
| `member_status` | `4` | 公会长或后台移除 |

- 公会长可以同时作为主播，但自播薪资和管理收益必须分链路记录。
- 一个有效成员关系内不得重复申请加入其他公会；存在待审核申请时不得重复申请。
- 入会通过时保存成员关系、政策版本、档位、比例和 X/Y/Z 快照。
- 离会或移除必须先完成离会结算和预支处理，再解除有效归属。旧成员关系及已结算快照保留，不清零结算快照中的钻石余额。

### 2.2 钻石流水与结算归属

| 场景 | 口径 |
| --- | --- |
| 普通礼物 | `1金币=2钻石` |
| Lucky 礼物 | `10金币=2钻石` |
| 无有效公会归属 | 只记录普通钻石流水，不生成政策工资 |
| 有效公会归属且政策有效 | 流水进入当前成员关系和政策的结算范围 |
| 月结或离会结算完成 | 保留结算快照；以周期、成员关系和快照唯一性防重 |

| 字段 | 含义 |
| --- | --- |
| `valid_diamond_amount_total` | 本期有效钻石流水 |
| `valid_diamond_balance_amount` | 本期有效钻石余额字段；自由政策主播侧使用该余额作为 `D_balance`，普通政策主播侧保留展示和对账，不替代 `actual_diamond_amount` 作为档位输入 |
| `actual_diamond_amount` | 当前周期实际钻石值；普通政策主播侧使用该值命中档位并计算超档，历史周期以结算快照中的记录值为准 |
| `invalid_diamond_amount_total` | 风控或无效钻石 |
| `normal_diamond_amount_total` / `lucky_diamond_amount_total` | 普通礼物 / Lucky 礼物钻石 |
| `exchange_diamond_amount` | 本期已确认兑换记录的钻石汇总；不得由有效钻石流水与有效钻石余额的差额推算 |

- 冻结、拒付和其他无效流水不计入有效钻石流水。
- 普通政策主播底薪 `X`、TG 奖励 `Z` 使用当期实际值 `actual_diamond_amount` 命中档位并计算超档；公会长分成 `Y` 仍使用有效钻石流水。自由政策月结/周结主播侧继续使用对应周期的有效钻石余额 `D_balance`，公会长侧使用有效钻石流水 `D_flow`。这些口径不得互相替代。
- 兑换钻石流水不作为工资基数，也不用于推算有效钻石余额；未确认兑换记录不计入汇总。
- 同一主播同一周期跨多个公会时，按成员归属时间段分别生成记录；同一业务事件只能归属一个公会。

## 3. 政策与工资计算

### 3.1 通用规则

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `policy_type` | `1` | TG 政策（月结），原普通政策 |
| `policy_type` | `2` | 自由政策（月结） |
| `policy_type` | `3` | 自由政策（周结），合法政策类型，不属于异常数据 |

- 先生成每个工资项，再在每个工资项内拆分金币工资和非金币工资，最后汇总角色工资。
- 历史结算必须读取快照，不得用当前政策或当前成员关系重算。
- 当前政策变更只影响未结算周期；结算周期、成员归属和政策快照共同确定结算结果。
- `policy_type=3` 只能进入周结链路和周结表，不得混入月结明细或月结结算；月结明细查询只接收 `1/2`，周结查询只接收 `3`。
- 月结明细与周结明细保持独立；“当月公会总薪资”是自然月累计汇总口径：月结沿用原有实时行/结算快照口径，周结仅汇总未结算行，已结算周结快照保留为明细和审计记录但不参与周结或本月公会总薪资；不得将周结记录写入或当作月结明细展示。

### 3.2 自由政策（月结）

自由政策不展示薪资等级、命中档位、超档步长、主播底薪或主播 TG 奖励。

月结自由政策标准：

| 参数 | 值 | 说明 |
| --- | ---: | --- |
| 总分成比 | `1.1` | 自由政策工资基数总分成参数 |
| 钻石换算美元比例 | `150000` | `150000` 钻石折算 `1 USD` |
| 主播分成比 | `0.8` | 主播侧分成比例 |
| 公会长分成比 | `0.2` | 公会长管理收益分成比例 |
| 强制充值比例 | `0.2` | 自由政策配置项；按对应业务字段使用，不替代工资项金币/非金币拆分比例 |

```text
主播工资基数 = 有效钻石余额 * 1.1 / 150000 * 0.8
主播总薪资 = 主播工资基数
主播金币工资 = 主播工资基数 * 金币工资比例
主播非金币工资 = 主播工资基数 * (1 - 金币工资比例)
主播总薪资 = 主播金币工资 + 主播非金币工资

公会长工资基数 = 有效钻石流水 * 1.1 / 150000 * 0.2
公会长管理收益 = 公会长工资基数
公会长金币工资 = 公会长工资基数 * 金币工资比例
公会长非金币工资 = 公会长工资基数 * (1 - 金币工资比例)
公会长管理收益 = 公会长金币工资 + 公会长非金币工资
```

- 主播侧使用有效钻石余额，公会长侧使用有效钻石流水；两者不相等时分别计算。
- 自由政策月结的主播侧使用当月有效钻石余额，公会长侧使用当月有效钻石流水；已结算历史仍以结算快照为准，不按当前规则重算。

### 3.3 自由政策（周结）

自由政策（周结）是独立政策类型，使用周结表和 UTC+3 自然周周期；周结使用本节独立参数，月结继续使用 3.2 节的月结参数。

```text
周主播工资基数 = D_balance * 0.8 / 130000 * 0.73
主播周总薪资 = 周主播工资基数
公会长管理收益基数 = D_flow * 0.8 / 130000 * 0.27
公会长周管理收益 = 公会长管理收益基数
每个工资项金币工资 = 工资项 * 0
每个工资项非金币工资 = 工资项 * 1.00
```

| 变量 | 口径 |
| --- | --- |
| `D_flow` | 指定自然周、指定公会、`policy_type=3` 范围内的有效钻石流水；排除冻结、拒付和其他无效流水 |
| `D_balance` | 指定自然周形成的有效钻石余额；主播侧工资基数，不得用 `D_flow` 替代 |
| 周期边界 | UTC+3 周一 00:00（含）至下周一 00:00（不含） |
| 钻石换算美元比例 | `130000`，表示 `1 USD` 对应的钻石数量 |
| 总分成比 | `0.8` |
| 主播分成比 | `0.73` |
| 公会长分成比 | `0.27` |
| 强制充值比例 | `0.2`；自由政策配置项 |
| 金币工资比例 | `0`；周结工资全部为非金币工资，不替代 `0.8` 总分成比 |

- 周结主播侧使用 `D_balance`，公会长侧使用同一成员的 `D_flow`；不得交叉使用。周结两侧使用本节的 `0.8 / 130000 / 0.73 / 0.27` 参数，不能沿用月结的 `1.1 / 150000 / 0.8 / 0.2` 参数。
- 公会长本人同时为周结主播时，主播工资和管理收益分别生成，主播工资计入主播总薪资，不重复计入管理收益。
- 每个工资项先拆分金币工资和非金币工资，再汇总角色工资；周结金币工资为 `0`，非金币工资为 `100%`，因此周结工资全部进入非金币工资口径。
- 周结进行中读取 `guild_salary_detail_weekly`；周结完成后读取 `guild_settlement_bill_weekly` 快照，不得用月结表重算。

### 3.4 普通政策

```text
确定有效钻石口径
-> 命中档位
-> 计算超档增量
-> 形成薪资基数
-> 按 X/Y/Z 拆分
-> 有效天扣减
-> 按工资项拆分金币和非金币工资
```

```text
完整超档步数 = FLOOR(MAX(0, 实际值 - 当前档目标值) / 超档步长)
超档增量 = 完整超档步数 * 单步超档金额
主播薪资基数 = 当前档基础薪资 + 以普通政策主播实际值 `actual_diamond_amount` 计算的超档增量
公会长分成基数 = 当前档基础薪资 + 以有效钻石流水计算的超档增量
主播底薪 = 主播薪资基数 * X
主播 TG 奖励 = 主播薪资基数 * Z
公会长分成 = 公会长分成基数 * Y
```

- 实际值刚好达到下一档目标时，直接命中下一档；未超过当前档目标时，超档增量为 `0`。
- 超出目标但不足一个完整步长时超档增量为 `0`；达到多个完整步长时按步数向下取整，不能计入不足一个步长的部分。
- 超档发生在 X/Y/Z 拆分之前。主播底薪和 TG 奖励按普通政策主播实际值 `actual_diamond_amount` 判断档位和超档，公会长分成按有效钻石流水判断档位和超档；不得以 `valid_diamond_balance_amount` 替代普通政策主播实际值。
- `X + Y + Z` 必须等于 `100%`。

### 3.5 新手保护与有效天扣减

- 新主播在当前成员关系 `joined_at` 所在自然月内处于新手保护期；保护期内不因有效天未达标扣减工资。
- 保护期结束后，普通政策有效天未达标时，主播底薪、主播 TG 奖励和对应公会长分成分别按 `85%` 结算，再拆分金币工资和非金币工资。
- 有效天未达标扣减比例为 `15%`。`effective_day_deduction_amount` 为主播底薪和 TG 奖励的扣减合计；公会长侧使用 `owner_effective_day_deduction_amount`。
- 普通政策存在 34、35 档，两档金币工资比例固定为 `5%`。实时工资和新生成结算必须将该比例写入政策与结算快照；已结算历史仍读取原结算快照，发现比例不一致时标记异常，不直接重算。

## 4. 工资展示与统计口径

### 4.1 主播薪资字段

| 页面字段 | 口径 |
| --- | --- |
| 本期有效钻石流水 | `valid_diamond_amount_total` |
| 本期有效钻石余额 | `valid_diamond_balance_amount`；自由政策主播侧的 `D_balance`，普通政策页面仍展示该独立余额字段 |
| 普通政策主播档位实际值 | `actual_diamond_amount`；用于主播 `X/Z` 命中档位及计算超档 |
| 薪资等级 | `salary_level`；自由政策展示 `--` |
| 有效天数 | `effective_days` |
| 扣减前主播底薪 / TG 奖励 | `salary_base_amount * base_share_rate` / `salary_base_amount * tc_reward_rate` |
| 有效天未达标扣减 | `effective_day_deduction_amount` |
| 主播底薪 / TG 奖励 | 普通政策下的客户端分项总额，均包含各自分配的金币工资 |
| 非金币工资 | `non_coin_reward_amount` |
| 金币工资 | `coin_reward_amount`，仅能提现金币 |
| 主播总薪资 | `non_coin_reward_amount + coin_reward_amount` |
| 主播已预支 | `advance_deduction_amount` |
| 主播薪资余额 | `non_coin_reward_amount - advance_deduction_amount + coin_reward_amount` |

- 普通政策客户端展示格式：`主播底薪 <总额>（含金币工资 <金额>）`、`主播TG奖励 <总额>（含金币工资 <金额>）`。
- 自由政策不产生普通政策底薪/TG 分项，客户端必须展示 `--`，不能用主播总薪资替代。

### 4.2 公会统计口径

| 页面 | 字段 | 口径 |
| --- | --- | --- |
| 客户端公会长薪资页 | 公会长总薪资 | 公会长管理收益，不含本人自播薪资 |
| 客户端公会长薪资页 | 公会长总薪资余额 | 本人主播总薪资 + 管理收益 - 公会长侧预支 |
| 客户端公会薪资页 | 主播总薪资 | 当前公会全部主播侧总薪资，含公会长自播薪资 |
| 客户端公会薪资页 | 公会长总薪资 | 当前公会管理收益，不重复加入自播薪资 |
| 客户端公会薪资页 | 公会总薪资 | 主播总薪资 + 公会长管理收益 |
| 客户端公会薪资页 | 公会薪资余额 | 公会总薪资 - 公会总预支 |
| 后台主播薪资页 | 公会长总薪资 | 当前主播记录贡献的管理收益，不含公会长本人自播薪资 |
| 后台公会薪资页 | 公会长总薪资 | 当前公会管理收益，不含公会长本人自播薪资 |

- 所有客户端总薪资和薪资余额均包含金币工资。
- 后台主播薪资页和后台公会薪资页统一按工资项拆分并汇总：公会总非金币薪资等于主播非金币薪资加公会长非金币管理收益，公会总金币薪资等于主播金币薪资加公会长金币管理收益，公会总薪资等于前两项之和。
- 公会长本人自播工资只计入主播总薪资一次；公会长总薪资只计管理收益，公会总薪资等于主播总薪资加公会长总薪资。
- `bill_owner_type=2` 的 `member_id=0` 是公会汇总行。汇总字段若未包含公会长侧金币工资，必须由按成员的金币分项补齐，不能把汇总行和成员行重复相加。
- 当月公会总薪资按自然月累计：月结成员按原口径读取月结实时行或月结快照；周结成员的当月各自然周明细均可展示，但仅未结算周结行计入周结汇总。两类可计入金额分别汇总后相加，已结算周结快照不进入本月公会总薪资。主播总薪资仍包含公会长本人自播工资，公会长管理收益不重复计入自播工资。

### 4.3 周结展示与周期筛选

| 页面/查询 | 周结口径 |
| --- | --- |
| 客户端公会薪资周数据 | 仅读取 `policy_type=3` 的当前周实时结果或已结算周快照 |
| 客户端公会长周数据 | 公会长管理收益；本人周结主播工资另计入主播总薪资，不重复加入管理收益 |
| 后台主播周薪资 | 按自然周、公会和成员关系读取周结明细；支持当前周实时和历史周快照 |
| 后台公会周薪资 | 主播总薪资 + 公会长管理收益；`member_id=0` 汇总行不得与成员行重复累加 |
| 月结明细查询 | 仅读取 `policy_type=1/2` 和月结表，不混入周结数据 |
| 当月公会总薪资汇总 | 月结按原口径汇总；周结明细完整读取，但仅未结算行计入自然月累计，已结算周结快照仅展示 |

- 当前自然周查询不得提前生成 `guild_settlement_bill_weekly` 或写入余额池。
- 已结算自然周必须读取周结账单快照，不能按当前政策、当前成员关系或实时流水重算。
- 周历史保存自然周起止标识、UTC+3 时区、政策快照、成员关系快照、`D_flow`、`D_balance`、工资拆分和结算状态。

### 4.4 成员按月结/周结分类展示

- 成员分类以当前有效成员关系的 `policy_type` 为准：`1/2` 为月结成员，`3` 为周结成员。
- 分类展示必须覆盖全部 `member_status=2` 的有效成员；不能因为当期工资明细尚未生成而省略成员。
- 公会长兼主播时，保留公会长角色标识，并按其主播政策进入月结或周结分组；公会长管理收益仍单独按 `bill_owner_type=2` 统计。
- 每组至少展示用户号、角色、政策类型和当期工资明细状态；缺少工资行时标记“暂无工资明细”，不将该状态直接解释为已确认收入为 0。
- 来源状态按工资明细逐行展示，不按成员合并；同一成员存在多个周期或多个来源时，分别展示每条明细的周期、来源和结算状态，例如分别列出“2026-09-14 已结算快照”和“2026-09-21 实时”，不得合并为“历史周结快照 + 当前周结实时”等单一状态。
- 展示顺序固定为“月结成员”在前、“周结成员”在后；月结组只读取月结表，周结组只读取周结表，禁止用工资明细来源反推成员所属分组。
- 月结和周结主播明细均按主播逐行展示公会长管理收益、主播底薪和主播 TG 薪资。`policy_type=1` 使用明细中的 `anchor_base_salary_amount`、`anchor_tc_reward_amount`；自由政策 `policy_type=2/3` 不产生普通政策底薪/TG 分项，展示 `--`。
- 公会长管理收益取同一成员关系对应的 `bill_owner_type=2` 行，金额为该行 `total_salary_amount + guild_coin_reward_amount`；公会长兼主播时，该管理收益与主播自播工资分开展示。
- 公会汇总也按周期展示：月结组分别汇总主播工资、公会长管理收益和月结公会薪资；本月累计口径中的周结组只汇总未结算行，已结算周结快照逐条展示但不参与本月累计。单独查询已结算历史周时，以所选周结快照汇总该周结果。本月公会总薪资为月结公会薪资与未结算周结公会薪资之和。
- 周期汇总不得把月结与周结的主播工资或公会长管理收益先混合后再标注来源；`member_id=0` 公会汇总行仍不得与成员管理收益重复相加。

### 4.5 后台薪资页面

- 1.4 后台薪资只覆盖“主播薪资”和“公会薪资”页面，统一使用“非金币薪资”；工资和可提现余额以 USD 展示，金币薪资字段展示美元金额，钻石字段展示钻石数量。
- 两页均不展示起始钻石余额、最终钻石余额、公会总薪资余额，以及预支、借支、待抵扣或对冲计算字段。
- 主播薪资页汇总区保留公会总非金币薪资、公会总金币薪资和公会总薪资，主播列表不重复展示这三项；“可提现余额（含金币）”位于列表最右侧。
- 公会薪资页保留公会总非金币薪资、公会总金币薪资和公会总薪资；成员总数与按周期归属快照去重的活跃主播数是不同指标。
- 当前未结束周期读取实时预计算结果；已结束且已结算周期读取同一版本的政策、归属、钻石输入和工资拆分快照。查询结果只能使用一种数据源，不拼接实时数据与结算快照。
- 汇总、列表、详情和导出必须使用相同筛选条件、周期、数据源、快照版本和数据权限；汇总覆盖完整筛选结果，不受分页影响，排序按完整结果集执行。
- 详情读取被选中的公会、主播及归属记录，不混入同一主体的其他公会记录，也不使用页面显示值重新计算工资。
- 导出覆盖完整筛选结果，金额与页面列表及汇总一致；记录导出人、导出时间、筛选条件和快照版本。空结果导出不得携带上次查询数据。

## 5. 余额池、提现与预支

### 5.1 余额池

| `pool_type` / `source_pool_type` | 含义 | 可用范围 |
| --- | --- | --- |
| `1` | 个人薪资余额 | 现金提现、提现金币、提现给公会长、预支抵扣 |
| `2` | 金币工资奖励余额 | 仅提现金币 |
| `3` | 主播转入薪资余额 | 现金提现或提现金币，不可提现给公会长 |

- 主播和公会长的非金币工资进入个人薪资余额；金币工资进入金币工资奖励余额。
- 主播提现给公会长审核通过后，金额进入公会长的主播转入薪资余额。

### 5.2 实时可提现余额（含金币）

- 主播可提现余额汇总当前个人薪资余额池、金币工资奖励余额池，以及已实际入账且仍符合提现条件的主播转入薪资余额。
- 已提现、已冻结、失败回滚尚未恢复、不可用或没有可用提现出口的金额不计入；金币工资可计入展示值，但仍只能提现金币。
- 可提现余额直接读取当前余额池，不从本期工资或公会总薪资推导；历史周期页面也展示当前实时值，实时变化不回写周期工资快照。
- 公会可提现余额汇总明确归属于当前公会的主播实时余额和公会长管理收益对应的实时余额。公会长本人主播余额归入主播侧，管理收益余额单独归因。
- 每个余额池在同一汇总中只计算一次，不得因多重身份或跨公会重复统计；无法明确归因公会的余额不猜测计入任何公会。
- 查询公会实时余额不创建独立公会钱包。提现、冻结或失败回滚恢复后，页面刷新读取余额池最新状态。

### 5.3 提现

| `withdraw_type` | 含义 |
| --- | --- |
| `1` | 提现金币 |
| `2` | 提现现金 |
| `3` | 提现给公会长 |

- 提现提交必须保存余额池、金额、扣减顺序和账户字段快照，并冻结申请金额。
- 审核拒绝必须释放冻结；审核通过才执行扣减和打款主链。终态记录不得重复审核、重复打款或重复回滚。
- 现金提现字段以 `/api/guild/withdraw/home` 返回的 `account_fields` 为准。
- 提现给公会长仅允许主播使用个人薪资余额；禁止金币工资奖励余额和主播转入余额。公会长本人不展示该入口。

### 5.4 预支

| `advance_type` | 含义 |
| --- | --- |
| `1` | 预支给本人 |
| `2` | 预支给其他收款人 |

```text
可预支金额 = max(0, 已结算且未提现、未转账、未冻结的非金币工资余额
                    - 已审核通过且尚未抵扣完的预支
                    - 待抵扣余额)
```

- 第一期不开放客户端自助预支，由后台发起并审核。
- 预支给他人时债务挂在预支人本人；月结只抵扣预支人的非金币工资。
- 金币工资不计入可预支金额，也不参与预支抵扣。
- 创建或审核通过预支后刷新实时工资；发放确认必须调用 `/internal/guild/advance/issue/confirm`。

## 6. 结算、快照与审计

| `settle_status` | 含义 |
| --- | --- |
| `1` | 待确认 / 待结算 |
| `2` | 已确认 / 已结算 |

| 动作 | 内部主链 |
| --- | --- |
| 刷新实时工资 | `POST /internal/guild/salary/realtime/refresh` |
| 生成月结 | `POST /internal/guild/settlement/monthly` |
| 生成周结 | UTC+3 每周一 00:00 锁定上一自然周，生成 `guild_settlement_bill_weekly` |
| 确认月结 | `POST /internal/guild/settlement/confirm` |
| 后台移除成员 | `POST /internal/guild/member/remove` |

### 6.1 指定公会月结触发

- 仅在用户明确要求结算指定公会编号和月份时触发；普通薪资查询不触发结算。
- 公会编号按 `guild_info.guild_no` 定位公会记录，取其内部主键作为 `guild_id`，并用该 `guild_id` 核对 `guild_salary_detail` 的目标月份记录。不得把 `guild_no` 当成 `guild_id`。
- 在测试环境 XXJob 任务管理中精确查找 `guild:monthly-settlement`，确认唯一匹配且任务启用后触发；任务参数为 `<guild_id>|<YYYY-MM>`。
- 示例：公会编号 `1022` 对应内部 `guild_id=24`，结算 `2026-09` 时传入 `24|2026-09`。
- 触发后核验 XXJob 执行结果及 `guild_settlement_bill` 中该 `guild_id`、月份的账单和状态。若已有已结算账单、执行状态不明确或结果缺失，停止并报告，不盲目重试。
- 结算月份只能由结算流程生成；不得直接改写已结算账单或工资明细的 `settlement_month`。

- 本月月结实时工资按 `guild_salary_detail` 预计算行读取，本周周结实时工资按 `guild_salary_detail_weekly` 预计算行读取；已结算工资分别按对应月结单或周结单快照读取。当月公会总薪资汇总时，月结按原口径计入，周结仅合并未结算行的金额；已结算周结快照保留为明细与审计依据，不参与汇总。
- 修正或迁移未结算实时薪资所属月份时，必须同步迁移/修正底层周期收入数据并校验关联的兑钻流水；月结收入来源为 `guild_member_income_monthly`，按 `guild_id`、`member_id`、`user_id` 和 `settlement_month` 对齐，核对 `diamond_amount_total`、`normal_diamond_amount_total`、`lucky_diamond_amount_total`、`invalid_diamond_amount_total`、`asset_adjustment_diamond_amount_total` 及 `last_occurred_at`。月有效钻石按 `max(diamond_amount_total - invalid_diamond_amount_total + asset_adjustment_diamond_amount_total, 0)` 计算；兑钻还需核对目标月份实时 `guild_salary_detail.month_exchange_diamond`。只改 `guild_salary_detail.settlement_month` 不会迁移底层收入，后续刷新实时工资会按目标月份重新读取收入并覆盖明细。周结同理，须迁移对应周收入汇总及周结兑钻数据，不能将月结来源表与周结来源表混用。
- 迁移前后须核对来源月和目标月的成员归属、收入汇总、兑钻记录及重复/缺失情况；不得把同一收入同时留在两个周期或重复计入。已结算周期及账单快照不得通过改月份迁移；需要纠正时应走单独的结算差错修复和审计流程。
- 使用新数据模拟历史月结时按《数据库表结构.md》中“使用新数据模拟历史月结的操作步骤”执行：测试环境先留存变更前数据并核对目标月份账单，再检查收入、有效天和兑钻输入；排除目标成员重复或重叠后迁移结算归属月份，保留真实流水发生时间；仅对已确认的失效实时账单链接解除关联，随后调用实时薪资刷新任务并核对结果；月结必须再次预检并经用户二次确认后触发，最后核验任务终态、账单与明细关联。任何已结算账单、快照或无法确认的来源状态都应停止操作。
- 月结必须保存流水、工资项、扣减、预支、余额池、成员关系和政策版本快照。确认后写入余额池并锁定该周期收入。
- 周结必须保存自然周、政策、成员关系、流水、工资项、拆分、余额池和结算状态快照；确认后写入余额池并锁定该周期收入。
- 同一周期、成员关系和结算归属不得重复结算；月结与周结分别按各自表和周期防重，离会已结算成员不得被重复处理。
- 已结算月份不能编辑兑钻；未结算月份编辑兑钻或调整政策、补偿礼物流、预支审核后，必须刷新实时工资。
- 周结只允许自由政策（周结）参与；周一结算只处理上一自然周，跨月、跨年自然周不得按月末拆分。
- 政策、成员关系、提现申请和后台资产操作均需保存对应前后快照和操作审计。
- 页面查询、排序、查看详情和导出均为只读操作，不得生成结算或历史快照，不得执行工资入账，也不得修改任一余额池。
- 结算中、结算失败或数据无法对账的记录不得展示为正式结算；结算重试必须关联原记录，且不得重复生成工资项或重复入账。
- 快照缺失、版本不一致、重复快照或归属缺失时标记数据异常，不拼接其他来源，也不按当前政策或当前成员关系补算。
- 实时余额与周期工资、兑换钻石与有效余额不一致时分别展示各自记录值，不自动修正或用差额替代工资基数。

## 7. 政策修改、CMS 与幂等

- `policy_type=1/2` 的月结政策仅可每月 `1` 日修改；`policy_type=3` 的周结政策仅可每周一修改；判断按当前政策，不按目标政策。
- 公会长不能替主播修改其本人政策；公会长调整主播政策沿用既有权限、次数和审计规则。
- 政策修改必须保存修改前后值、操作人、对象、时间和所属自然月，并创建新政策版本。
- CMS 公会管理优先展示 `guild_no`；薪资列表优先读取实时预计算或结算快照，不逐条临时重算。
- CMS 提现审核仅处理现金提现，但记录页必须覆盖金币、现金和提现给公会长三类记录。
- 所有资金、成员关系和状态变更接口必须幂等。重复提交不得造成重复冻结、入账、扣减、成员关系或结算快照。
- 结算快照缺失、同周期重复快照、汇总遗漏应标记异常并进入人工复核。

## 8. 后台权限、展示与数据质量

- 后台薪资查看、详情和导出分别校验权限及授权公会范围；无权限时页面入口和接口均不得返回薪资金额，修改查询条件不能越权读取或导出其他公会。
- 客户端公会长或管理员身份不自动获得后台薪资权限；只读权限不能修改结算结果或余额池，权限撤销后刷新或再次导出必须重新校验。
- 金额为 `0` 时展示 `0`。负数钻石输入、负数薪资结果、重复主播结算记录、重复公会快照、缺少政策或归属快照均按异常数据处理，不作为正常结果重复汇总。
- 金额展示沿用账务精度，前端不得另行舍入；超大金额不得遮挡相邻字段或操作入口。
- 中文、英文和阿拉伯语环境下字段、政策名称、金额、日期和单位必须保持完整且口径一致；阿拉伯语使用 RTL 布局。
