# Code Workspace Rules

This directory contains three independent codebases: two Java 17 backends and one Vue 2 admin frontend. Inherit `E:\Codex\Top\AGENTS.md`; these rules add code-level context for work below `code\`.

## Scope

- `top-app-api\` is a Maven reactor. Its modules are `common`, `model`, `service`, `web`, `job`, and `integration`.
- `top-room-api\` is a standalone Spring Boot monolith.
- `top-admin-api\` is a Vue 2.7 admin frontend built with Webpack 4; despite its name, it is not a backend service.
- Read `ARCHITECTURE.md` when a change crosses codebases, adds a cross-service workflow, or requires ownership and dependency mapping.
- Keep changes inside the requested codebase. Do not couple these codebases through direct source dependencies.
- Treat downloaded ZIP worktrees as source snapshots: confirm Git metadata and remote before proposing branch, pull, commit, or push operations.

## Post-Pull Documentation Review

After every successful pull of one or more repositories under `code\`, complete this review before reporting the pull task finished:

1. Record each repository's before/after commit and inspect the complete pulled range, including changed code, configuration, migrations, tests, and repository documentation. Do not infer a merge commit's contents from its title alone.
2. Review this `AGENTS.md` for stale instructions and durable new implementation constraints. Update rules when module ownership, entry points, operational contracts, validation requirements, or recurring verification expectations changed.
3. Review `ARCHITECTURE.md` for stale or missing system structure. Update it when responsibilities, dependency directions, data ownership, external integrations, persistence contracts, execution entry points, or cross-service workflows changed.
4. Keep transient commit details and feature changelogs out of both documents. Rules belong in `AGENTS.md`; stable ownership and interaction maps belong in `ARCHITECTURE.md`.
5. In the pull result, state separately whether each document was updated or remained valid, and name the evidence behind that decision. The review is complete only when every updated repository and both documents have an explicit conclusion.

## top-app-api

- HTTP execution starts in `app-api-web` at `com.app.api.AppApiApplication`; background execution starts separately in `app-api-job` at `com.app.api.JobApplication`.
- Preserve the direction `web -> service -> model/integration -> common`. Controllers translate HTTP concerns; business modules own transactions and rules; model owns entities and MyBatis mappers; integration owns third-party adapters.
- Payment and SMS routing use small seams (`IPayService`/`PayFactory`, `ISmsProvider`/`SmsFactory`). Add a new provider through the existing interface and factory registration. Prefer typed request/result objects when changing payment verification; do not extend channel-specific `Object...` knowledge into callers.
- Job dispatch uses `JavaJob` and `JobDispatcher`. Add task-specific behavior behind that seam rather than teaching consumers about individual task implementations.
- `UserController` and `UserServiceImpl` are already broad. Place new user behavior in focused modules for profile, relationships, account security, or wallet concerns; controllers should not acquire direct mapper dependencies for new business rules.
- Homepage identity labels combine live roles with the persisted `ln_user.identity` JSON array. Live labels remain coin agent, guild owner, then anchor; suppress the anchor label when the user is also a guild owner. Persisted editable identities accept codes 4-11 only, follow `UserIdentityEnum` order, and use lowercase underscore icon keys with `_ar` Arabic variants. Public discovery search accepts the public user code or an exact, currently valid good number, but must not match the internal `user_id`. Third-party coin-agent lookup accepts the same public identifiers and returns an absolute avatar URL plus the user's country code.
- Room visitor lists expose `user_code`, effective `good_number`, `is_good_number`, and `display_user_code` (good number first), plus the avatar-frame material under `special.avatar`. Keep these fields aligned with room-api room-management and pit-queue responses.
- ZeeOne is external-game provider type `2`. Client launch uses authenticated `/api/zeeone/session/generate`; provider callbacks use `/provider/zeeone/v1/api/**` without App JWT and must retain the vendor response envelope. Keep provider-specific launch/session logic in `ZeeOneGameService`, and do not leak Baishun query fields or valid-code behavior into ZeeOne responses.
- ZeeOne callbacks verify the original signed `reqbody`, a millisecond timestamp window, application ID, optional source-IP allowlist, and a Redis nonce before parsing business fields. Sessions are opaque, bound to app/user/game/room, and retained only for their configured TTL plus refresh grace. Balance changes require the callback game to match the session but use the session-bound room without requiring or validating callback `room_id`; they lock the derived order identity, persist the wallet mutation and `ln_game_detail` receipt in one transaction, reject mismatched duplicate payloads, and enqueue recharge consumption only for successful debits.
- Guild wallet-exchange changes that deduct salary must cover monthly and weekly policy routing (`policyType` 1/2/3), idempotent replay, and the rule that room-api realtime refresh failure does not roll back a successful exchange. A pending receipt retry re-resolves the active member but uses the receipt's persisted settlement month; realtime salary refresh runs after a newly created exchange commits. Keep these checks in focused wallet/Saga tests.
- Dynamic-avatar changes must preserve separate static and dynamic avatar storage, GIF/WEBP validation, cumulative entitlement expiry, and Unix-second timestamps. Every dynamic entitlement is display state and must leave the user's confirmed `head_picture` unchanged in storage; response assemblers accept JPG/JPEG/PNG as persistable static sources and otherwise use the default-avatar resolver. Expiry sync may rewrite `head_picture` only when a persistable static source exists. Replacing the confirmed static avatar clears the current dynamic asset, and the VIP dynamic-avatar privilege starts at VIP5. Keep dynamic status fields out of legacy message and push payloads unless their contract explicitly declares them.
- Recharge rewards may extend an existing dynamic-avatar entitlement with `grantDays` without replacing its asset; the entitlement source key remains idempotent and the existing dynamic URL is retained.
- Recharge reward notifications preserve recognizable detail rows even when quantity, duration, product, or localization fields are incomplete; use localized “unavailable” markers and log the incomplete source instead of silently dropping the row. IM reward details use HTML `<br>` separators, and a `good_number` reward appends the localized customer-service selection notice.
- Rejected recharge source events must leave their outbox row in a retryable failure state; mark the failure with the rejection reason before the next compensation attempt.
- Recharge-consumption backfill batches freeze their persisted Riyadh-time window and coin-agent target snapshot. Retries must reuse that window and completed target set, reject a changed launch cutoff, and remain compatible with legacy rows whose persisted target count proves the snapshot is complete. Backfill account type is the source-time coin-agent identity, not the user's current identity; external-game and lucky-gift consumption use multiplier `0.1`, while ordinary consumption uses `1.0`.
- Recharge tier reward status sync must support numeric tier keys and the legacy semantic key `highest_tier`; resolve the latter from the highest valid persisted achievement for the same user and period before updating source status.
- Recharge ranking responses must hydrate active user profiles before ranking; missing or deleted profiles are excluded from top, self, and historical results. Keep rank ordering deterministic across paged and fallback queries, and reactivate an invalid persisted tier achievement when the user reaches that tier again.
- Recharge deduction without an explicit event ID selects valid credit and consumption events from the current Riyadh month, orders them by persisted occurrence time (falling back to arrival time) and event ID, and exposes both before/after highest valid tier values. The local XXL-JOB development compose configuration uses `Asia/Riyadh` to match recharge activity windows.

## top-room-api

- The application entry point is `com.talo.roomapi.RoomApiJavaApplication`. HTTP controllers, RabbitMQ listeners, and XXL-JOB handlers are separate entry seams.
- Keep controllers and queue listeners thin: validate/parse transport data, delegate to a business module, and preserve failure propagation. Idempotency and retry behavior belong in the business module, not the listener.
- `GiftQueueProcessingService` owns gift-queue state transitions, idempotency, retry records, and downstream projections. Changes to gift processing must retain retry-safe behavior for duplicate or partially failed messages.
- `GuildMonthlySettlementTask` orchestrates monthly settlement: refresh real-time salary, generate bills, then confirm bills into balance pools. It calls `GuildSettlementQueryService`.
- `GuildWeeklySettlementTask` schedules the independent free-policy weekly path, while `GuildWeeklySettlementService` owns weekly income refresh, salary calculation, bill generation/confirmation, logged-in weekly salary queries, and leave/asset-adjustment refresh seams. `GuildWeeklyPolicyService` remains the policy gate. `GuildSettlementPeriodService` defines monthly and Monday-based weekly settlement keys in `Asia/Riyadh`, converting existing `Asia/Shanghai` DATETIME values at the boundary; confirmed anchor bills reject further income. Weekly policy changes are Monday-only, free weekly policy uses a zero coin-reward rate, and it does not support diamond exchange, asset adjustment, or advances.
- Monthly and weekly salary confirmation send localized notices for anchors and guild owners. A guild owner with an anchor identity receives aggregated owner earnings plus their own anchor salary; preserve RTL-safe dynamic text formatting and cover both cycles and notice paths in tests.
- Policy changes enforce the existing monthly/weekly opening windows and monthly change limit, then publish a delayed `GuildPolicyConversionMessage`; residue reconciliation remains the idempotent compensation owner.
- `GuildPolicySettlementResidueService` owns policy-conversion residue between monthly and weekly income/detail tables. Lock source rows, atomically merge into the target, migrate asset-adjustment amounts, and delete source rows only after a successful merge; preserve idempotency and keep billed target rows protected.
- Treat generation and confirmation as distinct operations. Confirmation changes bill state, balance pools, income locks, and notices; retain its transaction and conditional state-update behavior.
- Signed manual settlement endpoints aggregate monthly and current-week operations. Preserve separate monthly/weekly services and add their counts only at the transport result boundary.
- Validate monthly-job parameters strictly as `yyyy-MM` or `guildId|yyyy-MM`, and weekly-job parameters as `yyyy-MM-dd` Monday dates or `guildId|yyyy-MM-dd`. Invalid input must fail visibly; it must not silently widen execution to all guilds or another period.
- Gift debit wallet logs and recharge-consumption outbox rows must use the persisted gift record time and record type. Derive lucky-gift classification per persisted record and strip internal event fields before returning the client payload.
- Self-gifting is allowed on the ordinary gift paths. Lock and validate the sender wallet row before decrementing it, and derive the returned balance from that locked snapshot.
- Removing a user from a room persists that user in the room blacklist and schedules the blacklist cache projection; there is no separate temporary-kick Redis key or temporary-kick entry error. Room member lookup accepts internal user ID, public user code, or an exact, currently valid good number.
- Room-management user search accepts an exact public user code or currently valid good number, using the same predicate for rows and count. Room-management and pit-queue responses retain `user_code` and expose effective `good_number`, `is_good_number`, and `display_user_code`; room-management responses also include avatar-frame material under `special.avatar`.
- Gift score policy uses received coins as its base: ordinary gifts grant charm at `1.0`, while lucky gifts retain the `0.1` multiplier. Preserve the configured effective-time boundary when changing the policy.
- Withdrawal requests select one allowed source balance pool. Validate and deduct that pool only; coin-reward pools use their dedicated coin exchange rate, while personal-salary pools retain the configured general rate.
- Withdrawal source validation follows the current contract: coin withdrawal accepts personal salary, coin reward, or anchor-transfer pools; cash withdrawal accepts personal salary or anchor-transfer pools; transfer-to-owner accepts personal salary only. When no source is supplied, preserve the configured legacy priority order.
- Cash withdrawal currently has no date gate in `GuildWithdrawService`; restore the `Asia/Riyadh` day-1 check only when the business rule is re-enabled. Successful coin conversion, transfer-to-owner, and cash submit/approve/reject transitions send localized system notices; duplicate wallet-credit retries must not resend completion notices.
- Custom-gift entitlement and linked gift state belong to room-api's `app` datasource. App-api only scans the current `Asia/Riyadh` recharge month and calls signed `/internal/custom-gift/grant`; Room owns idempotent monthly grants, submit fees and wallet logs in one transaction, expiry and gift availability, and weekly Redis rankings. Preserve the `code/message/data` envelope on `/api/custom-gift/**` and `/internal/custom-gift/**`, and keep the two XXL-JOB handlers (`customGiftGrantQualifiedJobHandler` and `customGiftExpireJobHandler`) coordinated with the `ln_custom_gift_record` schema.
- A successful withdrawal-to-coin wallet credit and its `withdrawal_to_coin:<orderNo>` recharge outbox row belong to the same transaction. Duplicate wallet credits must not emit another outbox row; app-api consumes this source as a one-to-one credit event rather than a consumption event.
- `GuildSettlementQueryService`, `GuildWithdrawService`, and `RoomQueryService` are high-complexity modules. Before adding behavior, identify a narrow seam and extract or extend a focused module; do not add unrelated responsibilities to these classes.

## top-admin-api

- Execution starts in `src/main.js`. Business routes are discovered from `src/router/modules` and registered statically by `src/router/index.js`; the server-provided menu tree controls sidebar visibility, not route registration.
- Treat backend authorization as authoritative. `src/permission.js` and the button-permission directive are not loaded by `src/main.js`, so hiding a menu or button is not an access-control guarantee.
- Preserve the dependency direction `view -> src/api adapter -> src/utils/request.js -> CMS backend`. Views own presentation and interaction; API adapters declare endpoints; the request module owns transport concerns.
- Use `src/utils/request.js` as the HTTP seam. Do not add callers to legacy `requestHall.js`; it contains embedded credentials and divergent response behavior. When touching an existing caller, migrate it to the main request module without copying credential values.
- Session knowledge currently spans `router/index.js`, `store/modules/user.js`, `utils/auth.js`, and the sidebar. Authentication, logout, menu persistence, or expiry changes must keep those callers coherent or move them behind one focused session module.
- Add each business area under matching `views`, `api`, and `router/modules` paths. Keep new pages focused; extract forms, dialogs, data normalization, and reusable business behavior instead of extending already-large page files.
- `SearchTable` is a shared deep module for filters, tables, pagination, sorting, and actions. Add only behavior shared by multiple business areas; keep feature-specific rules in the feature module.
- `SearchTable` select filters take options from `field.options` or `field.attrs.options`, and pagination emits both the legacy page/size events and `pagination-change`. Preserve both contracts when changing shared table behavior.
- `SearchTable` operation slots in current business pages provide their own fixed-right `el-table-column`; keep row-dependent guards null-safe because the outer slot does not supply a row.
- Menu keys are an operational contract with the CMS database menu tree. Route changes that affect navigation must update the matching menu/permission SQL or delivery documentation.
- Gift and mount audio uses the existing CMS/OSS upload seam. Keep `sound_url` in the feature API and form model, accept MP3 only for the audio control, and preserve preview and clear/delete behavior when changing gift or mount forms.
- Game-data filters use `provider_type` to load the matching game options, and a provider change clears the selected `game_id`. Keep the selected provider in summary, detail, and export requests.
- Guild salary and anchor-settlement pages support both monthly and weekly periods. Keep `settlement_cycle`, `settlement_month`, and `settlement_week` mutually exclusive, and route policy-conversion compensation through `/guild/member/policy/conversion-compensation` with backend authorization.
- Guild salary and anchor-settlement list requests may pass `region`, `settle_status`, `data_view` (`realtime` or `snapshot`), and custom sort fields; preserve these filters and the expanded salary/owner summary fields when changing the pages.
- The guild-salary cycle selector maps weekly queries to `policy_type=3`; monthly queries omit `policy_type` so both monthly policies remain visible. Keep `settlement_month` and `period_start` mutually exclusive.
- Asset-operation recharge deduction preview uses `/guild/asset/audit/preview`; keep the old client export as a compatibility alias only. Generate a new request ID per operation and reuse it through that operation's preview/confirm flow.
- Recharge-deduction preview creates a fresh `client_request_id` for each new operation flow. Preserve that ID only across the matching preview-to-confirm transition; a new preview must receive a new ID rather than reuse browser-session state.
- The member list hides invitation-code and invitation-package columns, displays identity codes 1-11, and allows editing only codes 4-11 while preserving read-only live roles 1-3. When both guild-owner and anchor identities exist, hide the anchor label.

## Configuration And Data

- Keep credentials, tokens, connection strings, and third-party secrets in `.env`; use `.env.example` only for variable names and safe placeholders. Never add real fallback credentials to application profile files or logs.
- Profile selection, database topology, Redis DBs, RabbitMQ queues, and XXL-JOB names are operational contracts. Read the applicable profile before changing any of them and preserve compatibility unless the request explicitly changes the contract.
- Existing local profile files contain sensitive fallback values. Do not repeat those values in documentation, test fixtures, output, or new configuration.
- ZeeOne deployment settings use `ZEEONE_ENABLED`, `ZEEONE_APP_SECRET`, `ZEEONE_MERCHANT_ID`, `ZEEONE_PLATFORM`, `ZEEONE_SESSION_TTL_SECONDS`, `ZEEONE_REFRESH_GRACE_SECONDS`, and `ZEEONE_IP_WHITELIST`. Production must supply the secret externally with no real fallback value. The provider controller currently records exact callback requests and responses at INFO with a request ID for reconciliation, while suppressing internal exception messages and stack traces; do not duplicate these payloads in general access logs or add secret values outside this explicit callback audit path.
- Deployed compose profiles set `LOGGING_LOGBACK_ROLLINGPOLICY_MAX_HISTORY=3`; Logback XML keeps a configurable 30-day fallback for non-compose execution.

## Verification

- Run focused Maven tests for the affected repository and module. For cross-cutting changes, also compile the relevant application entry module.
- Changes to payment/SMS adapters require contract tests. Changes to queue processing require duplicate-delivery and failed-retry coverage.
- Changes to ZeeOne require tests for raw-body signature tampering, timestamp and nonce replay, IP allowlisting, session identity/expiry/refresh, game binding and session-owned room attribution, concurrent duplicate orders, duplicate-payload mismatch, wallet rollback, insufficient balance, debit outbox emission, provider response fields, callback audit logging, and repeatable game seed data. The seed refreshes operational game fields on rerun while preserving non-empty icons; validate statement delimiters and provider-scoped status updates before executing its final game-selection statements.
- Changes to homepage identities require ordering, invalid-code filtering, guild-owner/anchor precedence, Arabic icon suffix, JSON mapping, public-code/active-good-number lookup tests, and proof that internal user IDs are not searchable.
- Changes to guild settlement require tests for month and guild targeting, reruns, partial failure, pending-to-confirmed transition, balance-pool writes, and income locks. Add a direct task test when changing `GuildMonthlySettlementTask` parameter parsing or orchestration.
- Changes to dynamic avatars require tests for static/dynamic fallback, entitlement expiry, upload authorization and format validation, response-field compatibility, and expiry-job repair.
- Changes to dynamic-avatar reward grants require tests for idempotent extension without asset replacement.
- Changes to reward notification formatting require tests for dynamic-avatar details, VIP level labels, localized asset names, and incomplete-field fallbacks.
- Changes to recharge-consumption backfill require tests for immutable batch windows, frozen target snapshots, source-time account identity, external-game/lucky-gift multipliers, interrupted snapshot recovery, legacy-row compatibility, and duplicate-safe retries.
- Changes to recharge tier reward compatibility require numeric-key and `highest_tier` status-sync tests.
- Changes to recharge ranking or tier-impact diagnostics require deleted-profile exclusion, deterministic paging/fallback, uppercase `TOP1`-`TOP5` award group output, invalid-achievement reactivation, current-Riyadh-month deduction selection, and before/after highest-tier tests.
- Changes to weekly settlement require tests for Riyadh Monday period validation and Shanghai DATETIME conversion, the fixed 73% anchor/27% owner split, policy switching and delayed conversion messages, weekly income routing, duplicate/retry handling, confirmed-bill rejection, leave-time income locking and refresh, settlement generation/confirmation, guild/date compensation parameters, and localized anchor/owner completion notices.
- Changes to custom gifts require tests for signed grants and monthly idempotency, concurrent submit/version checks, fee debit and wallet-log rollback, expiry and cache invalidation, ranking updates, and the App-to-Room grant response contract.
- Changes to policy-conversion residue require tests in both directions for source locking, atomic target merge, asset-adjustment migration, billed-target protection, duplicate delivery, and source deletion after success only.
- Changes to gift consumption projections require month-boundary tests proving wallet logs and outbox events share the persisted gift timestamp and per-record lucky classification.
- Changes to gift score policy require ordinary `1.0` and lucky `0.1` charm multiplier coverage across the configured effective-time boundary.
- Changes to withdrawal-to-coin crediting require atomic wallet-log/outbox tests and duplicate-credit tests that assert no second outbox event.
- Changes to recharge source compensation require tests for rejected events remaining retryable with their rejection reason.
- Treat the `top-app-api` batch start scripts as stale until their hard-coded checkout paths are corrected; use the Maven module and the active profile as the source of truth for local startup.
- For `top-admin-api`, run the applicable focused script in `scripts\` and then `yarn build:dev`; use `yarn build` for production-build changes. The project has no general test or lint script, and some wallet checks require a sibling `manage-api` checkout, so report unavailable prerequisites explicitly.
- `top-admin-api` uses Webpack 4 and Node Sass 5. Use the project-compatible Node version; when Node 17+ fails on OpenSSL compatibility, set `NODE_OPTIONS=--openssl-legacy-provider` for that command.
