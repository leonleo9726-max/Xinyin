## 二、开发速读版

### 2.1 一句话业务变化

公会政策由两种扩展为三种，在保留原两种月结政策的基础上新增“自由政策（周结）”；周结只改变结算周期和统计时间维度，工资计算仍沿用自由政策，结算结果继续进入现有工资拆分、余额池、提现和历史快照链路。

### 2.2 三种政策并存关系

| 正式展示名称 | 结算周期 | 计算模型 | 1.3 处理 |
|---|---|---|---|
| TG政策（月结） | 自然月 | 沿用现有 TG/普通政策 | 原“普通政策”展示名调整；计算和统计不变 |
| 自由政策（月结） | 自然月 | 沿用现有自由政策 | 原“自由政策”展示名调整；计算和统计不变 |
| 自由政策（周结） | 自然周 | 沿用现有自由政策 | 1.3 新增第三种政策 |

### 2.3 核心时间和筛选规则

- 周结周期为自然周。
- 按 UTC+3，每周一 00:00 结算上一自然周的薪资数据；周区间左闭右开。
- 主播更改政策按当前政策限制：自由政策（周结）仅每周一，TG政策（月结）和自由政策（月结）仅每月1号；更改成功后，当天更改前的流水和余额也计入新政策，见 3.5。
- 两种月结政策可以同时筛选。
- 任一月结政策不能与“自由政策（周结）”同时筛选。
- 月结政策联动月选择器；周结政策联动周选择器。
- 周数据不能混入两种月结政策的数据。
- 历史周数据读取已结算周快照，不按当前政策重新计算。

### 3.4 周期边界

| 规则项 | 规则 |
|---|---|
| 周期类型 | 自然周，不是滚动 7 天 |
| 结算时点 | UTC+3 每周一 00:00 |
| 结算对象 | 结算时点之前刚结束的上一自然周 |
| 区间表达 | 周一 00:00（含）至下周一 00:00（不含）；沿用历史周期左闭右开口径，边界时刻新产生的数据归新周 |
| 时区 | UTC+3；周统计、结算、客户端周历史、后台周查询和导出使用同一业务时区 |
| 月结政策 | 原统计方式、计算方式和时间维度不变 |

### 3.5 主播更改政策：开放日期与当天数据归属

#### 开放日期与限制提示

按用户更改前的当前政策判断是否允许更改，不按目标政策判断。以下规则替代原“所有政策仅每月 1 号可更改”的统一日期限制；不据此新增操作角色权限、入口或修改次数规则。

| 用户当前政策 | 允许更改日期 | 非开放日期处理 | Toast文案 |
|---|---|---|---|
| 自由政策（周结） | 仅每周一 | 不允许提交政策更改，原政策及数据归属保持不变 | 用户当前为周结政策，仅支持在每周一更改政策 |
| TG政策（月结） | 仅每月1号 | 不允许提交政策更改，原政策及数据归属保持不变 | 用户当前为月结政策，仅支持在每月1号更改政策 |
| 自由政策（月结） | 仅每月1号 | 不允许提交政策更改，原政策及数据归属保持不变 | 用户当前为月结政策，仅支持在每月1号更改政策 |

#### 更改当天的流水与余额

- 更改成功后，当天更改政策前的流水和余额也计入新政策；不能仅从点击更改成功的时刻开始按新政策统计。
- 当天更改前和更改后的数据按新政策归属，进入新政策对应的月结或周结统计与计算；同一笔数据不能在旧政策与新政策中重复累计。
- 更改当天流水、余额的政策归属发生调整，但不把流水和余额合并成同一计算基数，也不将账户存量余额当作一笔新增流水或新增余额入账。有效流水与有效余额仍按各自既有口径参与工资计算，不新增余额加减公式。
- 客户端相关实时薪资、后台主播薪资、公会薪资及导出均按上述新归属读取；不改变各页面已确认的筛选控件、日期选择器和默认值。
- 保留更改前后政策、操作人、操作对象、操作时间、归属日期、对应结算周期及当天数据转归结果，使后续工资计算和快照能够解释更改前的当天数据为何采用新政策。
- 既有已结算历史不因当前政策更改而自动重算。若当天数据已因离会等操作完成结算，再发生政策更改，与“当天更改前数据计入新政策”的冲突如何处理，仍需确认，不能静默重算或重复入账。

日期判断时区及当天已结算数据的处理边界见 P0-04；原月结历史规则不能覆盖本次已确认的周一开放规则和当天归属规则。

## 四、新增政策：自由政策（周结）

### 4.1 政策定位

“自由政策（周结）”是与“自由政策（月结）”“TG政策（月结）”并存的第三种政策，不替换任何现有政策。

周结与自由月结的关系：

- 计算模型相同；
- 统计和结算周期不同；
- 快照周期标识不同；
- 客户端周数据、后台周查询和周导出均只读取周结数据；
- 已结算历史不因当前政策变化而改算。

### 4.2 政策配置

| 配置项 | 1.3 值 | 用途 |
|---|---:|---|
| 分成比 | 0.8 | 代入自由政策工资计算 |
| 钻石换算美元比例 | 130000 | 每 1 USD 对应的钻石数量 |
| 强制充值工资比例 | 0.2 | 即金币工资奖励比例；每个工资项的 20% 为金币工资，剩余 80% 为非金币工资 |
| 主播分成比例 | 0.73 | 代入主播工资计算 |
| 公会长分成比例 | 0.27 | 代入公会长工资计算 |

### 4.3 工资计算

经三份历史文档对照，公会 1.1、1.2 均未修改薪资与资金链，因此周结政策沿用公会 1.0 已确认的自由政策计算模型，只把计算、结算和快照周期从自然月切换为自然周。开发不得另建一套“周结专用工资公式”，也不得把自由政策的主播侧计算基数和公会长侧计算基数混为同一个字段。

#### 4.3.1 周期、对象与变量

以下公式均针对一个待结算自然周、一个公会归属和一个“自由政策（周结）”政策快照执行：

| 变量 | 业务含义 | 取值要求 |
|---|---|---|
| `W` | 当前计算对应的自然周 | UTC+3 每周一 0 点结算上一自然周，区间左闭右开 |
| `G` | 数据归属公会 | 按主播、自然周、公会及归属时间段/快照分别成单；离会前结算原公会数据，见 8.3 |
| `D_flow` | 本周有效钻石流水 | 仅汇总 `W + G + 自由政策（周结）` 范围内的有效流水；旧版规则中，非幸运礼物按 `1 金币 = 2 钻石`、幸运礼物按 `10 金币 = 2 钻石`换算，再排除冻结、拒付及无效流水 |
| `D_balance` | 本周有效钻石余额 | 读取既有自由政策在该自然周形成的有效钻石余额结算结果；它是主播工资基数，不等于本周有效钻石流水，也不使用公会长侧流水公式反推 |
| `R_total` | 分成比 | 1.3 配置为 `0.8` |
| `R_anchor` | 主播分成比例 | 1.3 配置为 `0.73` |
| `R_leader` | 公会长分成比例 | 1.3 配置为 `0.27` |
| `D_per_USD` | 钻石换算美元比例 | 1.3 配置为 `130000`，含义为 `1 USD` 对应的钻石数量 |
| `R_coin` | 金币工资奖励比例 | 即强制充值工资比例，周结取 `0.2`；仅用于工资项拆分，不替代总工资计算的分成比 |

> 旧版材料没有给出可独立重建 `D_balance` 的完整加减公式。因此本文保留它作为既有结算结果字段，不用“起始余额 + 流水 - 兑钻”等对账字段拼出一套未经确认的新算法。

#### 4.3.2 角色工资公式

| 工资项 | 计算公式 | 计算基数与归属 |
|---|---|---|
| 单个主播周总薪资 `S_anchor` | `D_balance × R_total ÷ D_per_USD × R_anchor` | 使用该主播在 `W + G` 下的本周有效钻石余额；包含后续待拆分的金币工资和非金币工资 |
| 单个主播贡献的公会长周薪资 `S_leader_contrib` | `D_flow × R_total ÷ D_per_USD × R_leader` | 使用该主播在 `W + G` 下的本周有效钻石流水；归属对应公会长管理收益 |
| 公会主播周总薪资 | `Σ S_anchor` | 汇总该公会本周纳入周结的主播侧工资项；公会长本人作为主播且符合周结范围时，其主播侧工资按同一公式独立计算并计入 |
| 公会长管理周薪资 | `Σ S_leader_contrib` | 汇总该公会本周所有有效周结主播贡献的公会长侧工资项 |
| 公会周总薪资 | `公会主播周总薪资 + 公会长管理周薪资` | 两侧均使用同一自然周、同一公会归属和同一结算快照版本 |

代入 1.3 配置后：

- 单个主播周总薪资 = 本周有效钻石余额 × `0.8` ÷ `130000` × `0.73`。
- 单个主播贡献的公会长周薪资 = 本周有效钻石流水 × `0.8` ÷ `130000` × `0.27`。

公会长本人兼主播时，必须先生成“本人主播工资项”和“公会长管理收益项”，再分别完成金币/非金币拆分和角色汇总，不能把两类工资先合成一个金额后倒拆。公会长总薪资只包含管理收益，不包含本人主播薪资。本人主播薪资计入主播总薪资，在公会总薪资中只累计一次。

#### 4.3.3 金币工资拆分与余额池

按三份历史文档中仍适用的工资拆分规则及本次业务确认，周结处理顺序为：`逐工资项计算 → 每项拆分金币/非金币工资 → 按角色汇总 → 写入余额池 → 生成周结快照`。

对每个主播工资项和公会长工资项分别执行：

| 结果项 | 计算/处理口径 |
|---|---|
| 金币工资 | `工资项 × R_coin = 工资项 × 0.2`；进入金币工资奖励余额，只能走金币工资对应的金币提现出口 |
| 非金币工资 | `工资项 × (1 - R_coin) = 工资项 × 0.8`；进入工资型余额处理 |
| 工资型余额池入账 | 本期非金币工资，按主播/公会长角色进入对应个人薪资余额 |
| 金币工资余额池入账 | 当前工资项拆出的金币工资；不进入现金提现、提现给公会长 |
| 主播转入薪资余额 | 仅承接既有“提现给公会长”审核通过后的转入金额，与周结原始工资项分开记录，不计入本周工资重算 |

> 强制充值工资比例即 `R_coin = 0.2`，在角色工资项算出后拆分；总工资公式的分成比仍为 `R_total = 0.8`。两者作用步骤不同，不得混用。

#### 4.3.4 计算时点与结果性质

| 场景 | 计算与读取规则 |
|---|---|
| 自然周进行中 | 如页面展示进行中数据，只能作为未结算结果；默认展示当前周还是最近已结算周见 P1-07 |
| 周一 0 点触发结算 | 以 UTC+3 关闭上一自然周，锁定该周政策、成员关系、有效流水、有效余额、工资拆分和余额池结果 |
| 结算成功后 | 形成正式周结快照；客户端历史、后台查询、导出均读取该快照 |
| 结算失败/重试 | 不得重复生成工资或重复写入余额池；恢复处理须关联原结算记录、归属快照和已入账结果，不得将已结算的离会记录再次入账 |
| 政策或公会关系后续变化 | 政策更改按当前政策判断开放日期；更改成功后，当天更改前的流水和余额也计入新政策且不重复统计，见 3.5。已结算历史不自动重算；跨公会归属继续按 8.3 处理，当天已结算数据与政策更改冲突见 P0-04 |

### 4.4 结算后处理

周结工资形成后，继续沿用现有自由政策资金链：

1. 按现有规则拆分金币工资和非金币工资；
2. 非金币工资进入现有工资型余额池；
3. 金币工资进入金币工资余额；
4. 生成周结政策、关系、统计结果和金额快照；
5. 客户端历史、后台查询和导出读取同一周期快照。

第 1 步按金币工资 20%、非金币工资 80% 拆分。结算完成并生成快照、余额池结果后，按历史规则清空该次已结算的主播钻石余额，避免在后续周期重复计薪。

### 4.5 结算结果状态

1.3 脑图只定义结算时点和结算成功后的数据用途，没有新增结算状态枚举。结算中、结算失败、重试和人工补算状态继续沿用现有版本；若现有版本无法覆盖周结，需要另行确认，不在本文擅自增加状态。

### 4.6 周结数据表隔离与字段落地

周结与月结使用独立明细表和账单表，避免跨周期查询、历史重算和重复入账：

| 表 | 用途 | 关键周期字段 | 读取边界 |
|---|---|---|---|
| `guild_salary_detail_weekly` | 自由政策（周结）实时工资明细及账单关联明细 | `period_start`，UTC+3 周一日期 | 当前周读取实时行；正式周结后通过 `settlement_bill_id` 关联周结账单 |
| `guild_settlement_bill_weekly` | 自由政策（周结）正式结算账单和历史快照 | `period_start`，UTC+3 周一日期 | 已结算周读取账单快照，不按当前政策或实时流水重算 |

实施约束：

- `policy_type=3` 只写入周结表；`policy_type=1/2` 继续写入月结表，月周数据不得混查。
- `guild_salary_detail_weekly` 未生成正式账单时 `settlement_bill_id=0`；生成周结账单后关联 `guild_settlement_bill_weekly.id`。
- `bill_owner_type=1` 为主播工资，`bill_owner_type=2` 为公会长管理收益；`member_id=0` 为公会汇总行，不能与成员行重复累加。
- 周结明细和账单按 `guild_id + member_id + period_start + bill_owner_type` 幂等；账单号 `bill_no` 唯一。
- 周结账单必须保存自然周、政策、成员关系、公会归属、`D_flow`、`D_balance`、工资项、金币/非金币拆分、扣减、余额池结果和结算状态快照。
- 当前周查询不生成正式账单、不提前入账；UTC+3 每周一 00:00 只结算刚结束的上一自然周。

#### 周结主播薪资字段矩阵

| 字段 | 周结计算 / 取值规则 | 业务用途 |
|---|---|---|
| 结算政策 | 读取所选自然周的政策绑定快照，固定为“自由政策（周结）” | 区分月结与周结数据，历史不读当前政策 |

| 最终钻石余额 | 读取自然周结束或结算时的余额快照 | 结合起始余额、兑换钻石及调整项对账；不反向替代有效余额结算结果 |
| 兑换钻石 | 汇总该周已确认兑换/转出的钻石记录 | 解释钻石余额变化，不直接作为工资金额 |
| 本期有效钻石流水 | 读取该主播 `W + G` 范围内的 `D_flow` | 公会长侧工资基数及对账字段 |
| 本期有效钻石余额 | 读取该主播 `W + G` 范围内的 `D_balance` | 主播侧工资基数 |
| 主播总薪资 | `D_balance × 0.8 ÷ 130000 × 0.73` | 主播本周拆分前应发总工资 |
| 金币工资 | `主播总薪资 × 0.2` | 进入金币工资奖励余额；强制充值工资比例即金币工资比例 |
| 非金币工资 | `主播总薪资 × 0.8` | 进入工资型余额 |
| 主播薪资余额 | 结算汇总字段为 `主播总薪资`；底层余额池仍须拆分金币工资余额和非金币工资余额 | 结算结果与余额池对账 |
| 贡献公会长分成 | `D_flow × 0.8 ÷ 130000 × 0.27` | 归属该周、该公会的公会长管理收益 |
| 可提现余额 | 读取结算后允许进入对应提现出口的余额池结果；不得把金币工资直接算入现金可提现金额 | 提现资格与资产对账 |
| 通过主播转账金额 | 读取既有主播转入薪资记录，不作为本周工资公式输入 | 解释账户余额来源，避免与周薪重复累计 |

#### 后台计算顺序

1. 按自然周、主播、政策快照和公会归属筛选待结算数据。
2. 分别生成 `D_flow` 与 `D_balance`；两者用途不同，不能互换。
3. 计算主播总薪资和该主播贡献的公会长分成。
4. 对每个工资项分别按 20% 拆金币工资、80% 拆非金币工资。
5. 将金币工资与非金币工资分别写入对应余额池。
6. 生成主播周薪资记录、公会长贡献记录及同版本周结快照。
7. 汇总页、列表页、详情页和导出读取同一计算结果；已结算周不允许页面查询触发重算。

#### 政策更改当天的数据归属

政策更改成功后，当天更改前的流水和余额也按新政策参与薪资计算。查询、汇总、列表和导出按 3.5 读取转归后的数据，旧政策侧不重复保留同一笔统计结果；已结算历史与异常边界仍按 3.5 处理。本条只调整数据归属，不改变本页筛选方式。

#### 同周期多公会

- 用户在同一自然周加入多个公会时，需要形成多条属于不同公会的主播薪资数据。
- 后台主播薪资列表按公会分别展示这些记录，不能把不同公会的周薪合并为一条。
- 每条记录只归属该自然周内对应的公会薪资数据。
- 同一公会内多次加入形成不同归属时间段/快照的，保留独立结算记录；公会汇总时只累计一次，详见 8.3。

#### 导出

- 支持导出筛选后的“自由政策（周结）”数据。
- 导出数据范围与当前有效的周结政策筛选、自然周和其他已生效筛选条件一致。
- 导出字段结构沿用现有主播薪资导出，不根据原型表格列另行扩展。
- 导出文件名、同步/异步方式和历史范围未被脑图定义，本次不新增规则。

#### 周结公会薪资字段矩阵

以下工资公式同时用于所选自然周的实时计算和历史结果解释。已结束周读取历史数据；当前周读取同口径实时计算结果。表中的结算快照、结算时余额及入账结果仅适用于已结算数据，不能在当前周查询时提前生成或入账。

| 字段 | 周结计算 / 取值规则 | 对账要求 |
|---|---|---|
| 公会总数 | 统计当前周结筛选结果中的公会记录数 | 同一公会同一自然周同一快照版本只计一次 |
| 活跃主播数 | 统计该周已进入有效结算范围的周结主播数 | 不得用当前成员数覆盖已结算周的成员范围 |
| 本期有效钻石流水 | `Σ 各主播 D_flow` | 必须等于该公会主播明细中有效流水之和 |
| 本期有效钻石余额 | `Σ 各主播 D_balance` | 必须等于该公会主播明细中有效余额之和 |
| 主播工资总额 / 主播总薪资 | `Σ（各主播 D_balance × 0.8 ÷ 130000 × 0.73）` | 必须先逐主播计算后汇总，不允许用公会总有效余额一次计算后替代分账 |
| 公会长工资总额 / 公会长总薪资 | `Σ（各主播 D_flow × 0.8 ÷ 130000 × 0.27）` | 只汇总公会长管理收益，不包含本人主播工资 |
| 当前周期总工资 / 公会总薪资 | `主播工资总额 + 公会长管理工资总额` | 两部分必须来自同一自然周、同一公会；历史数据使用同一快照版本，当前周使用同口径实时结果，不跨两类结果拼接 |
| 公会总金币工资 / 公会金币工资 | `Σ 各工资项金币工资` | 由逐工资项拆分结果汇总，不允许在公会总薪资上一次性倒拆 |
| 公会总非金币工资 | `Σ 各工资项非金币工资` | 用于工资型余额入账 |
| 公会总薪资余额 / 公会总余额 | `公会总薪资` 的结算汇总结果 | 底层仍应满足：金币工资余额 + 非金币工资余额；不能直接等同现金可提现余额 |
| 起始钻石余额 | 汇总/读取自然周开始时的公会维度余额快照 | 只用于余额变动对账，不直接参与工资公式 |
| 最终钻石余额 | 汇总/读取自然周结算时的公会维度余额快照 | 与起始余额、兑换钻石及调整结果共同解释余额变化 |
| 兑换钻石 / 公会总兑换钻 | `Σ 该周已确认兑换钻石记录` | 不直接等同有效钻石余额或工资金额 |
| 结算快照版本 | 已结算周读取对应结果版本；当前周实时数据不作为已结算快照 | 历史汇总、列表、详情和导出禁止跨版本拼接，实时查询保持同一周期和政策范围 |

#### 公会总账与分账校验

- 公会汇总必须由主播级周结记录与公会长侧贡献记录向上汇总，不能只有一个无法下钻的总结果。
- `公会总薪资 = 主播工资总额 + 公会长管理工资总额`。
- `公会总金币工资 = Σ 主播侧金币工资 + Σ 公会长侧金币工资`。
- `公会总非金币工资 = Σ 主播侧非金币工资 + Σ 公会长侧非金币工资`。
- 同一笔主播工资和同一笔公会长贡献在一个公会周总账中只能累计一次。

#### 政策更改当天的数据归属

政策更改成功后，当天更改前的流水和余额也按新政策参与薪资计算。查询、汇总、列表和导出按 3.5 读取转归后的数据，旧政策侧不重复保留同一笔统计结果；已结算历史与异常边界仍按 3.5 处理。本条只调整数据归属，不改变本页筛选方式。

- 公会薪资汇总和列表必须按公会归属统计，不得把用户在不同公会的记录合并到错误公会。
- 已结算周数据读取对应公会和自然周的快照。

#### 导出

- 结算周期为月结时，沿用现有导出，范围包含所选自然月的自由政策（月结）和TG政策（月结）公会薪资数据。
- 结算周期为周结时，仅导出所选自然周的自由政策（周结）公会薪资数据；自然周口径使用 UTC+3。
- 导出与页面查询采用相同的结算周期、日期和政策范围：已结束周期读取历史薪资，当前周期读取实时薪资；已结算历史按对应归属快照读取。
- 导出字段结构沿用现有公会薪资导出，不从原型表格列推导新增字段。

### 7.1 主播/公会长—金币工资说明与全部提现

#### 对应原型

![主播/公会长—金币工资奖励说明](公会需求1.3原型图/主播_公会长-金币工资奖励说明.jpg)

#### 页面改动

在金币工资说明区域新增“全部提现”按钮。

| 页面元素 | 1.3 规则 |
|---|---|
| 全部提现 | 新增；以确认提现弹窗打开时的全部可用金币工资金额作为本次申请金额 |
| 确认提现金额弹窗 | 点击“全部提现”后显示 |
| 提现金额 | 显示并锁定确认提现弹窗打开时的全部可用金币工资金额 |
| 预估获得金币 | 根据金币工资美元金额和 `1 USD = 5000 金币` 自动换算 |
| 确认提现 | 按弹窗锁定金额校验可用余额、冻结并生成申请；审核通过后扣减及发放金币，不在点击时直接完成发放 |

#### 计算公式

- 预估获得金币 = 确认提现弹窗打开时锁定的金币工资金额（USD）× 5000。
- 金币工资专属提现比例：`1 USD = 5000 金币`。

#### 金额锁定、审核与失败处理

沿用 1.0 的 5.5、6.7 提现金币，以及 9.7 后台提现审核、9.8 提现记录；1.1、1.2 未修改该链路。本次专属入口只处理金币工资余额。

| 场景 | 处理规则 |
|---|---|
| 打开确认提现弹窗 | 读取当时全部可用金币工资，锁定申请美元金额与对应预估金币；打开弹窗本身不冻结、不扣减 |
| 弹窗打开后余额增加 | 本次仍使用弹窗打开时金额，新增余额不自动追加到本次申请 |
| 点击确认提现 | 重新校验金币工资可用余额能否覆盖已锁定金额；校验通过后仅冻结锁定金额，生成 Waiting 申请并记录余额池及冻结结果 |
| 当前余额不足 | 不得按旧弹窗金额超额扣减，也不得自动改成较小金额提交；不生成有效申请，沿用历史余额不足提示；不新增自动刷新或自动改额提交规则 |
| 取消 | 关闭弹窗，不生成申请、不冻结、不扣减 |
| 审核通过 | 校验冻结结果，进入审核通过待发放，正式扣减锁定金额并按 1 USD = 5000 金币发放 |
| 审核拒绝 | 记录拒绝原因，释放本申请冻结金额回原金币工资余额池 |
| 发放失败 | 进入失败回滚链路，按原申请恢复冻结或已扣减结果；保留失败及回滚状态，不将失败直接写为成功或改回 Waiting |
| 重复处理 | 同一申请只允许一次有效审核、扣减和发放；重试关联原申请状态和结果，不重复冻结或发放 |
| 记录追溯 | 保留弹窗锁定金额、预估金币、申请金额、来源余额池、冻结、审核、发放及回滚结果；客户端明细与全局记录展示位置仍见 P1-04 |

#### 两个“全部”入口的边界

- 本次新增的“全部提现”只处理金币工资。
- 原普通提现表单中的 `All Balance` 属于现有功能，不因本次新增按钮而改变含义。
- 两个入口不能共用同一个可提现基数或换算比例。

#### 原型冲突

原型示例为 `$1212 → 12120000 金币`，该数值不符合脑图的 `1 USD = 5000 金币`。正式需求只采用脑图比例，原型示例不得作为计算依据。

原型中的“提现成功”弹窗未被脑图定义，本次不写成正式页面流程。

## 八、快照、历史和跨公会归属

### 8.1 周结快照

周结完成后，沿用现有自由政策快照原则，并增加自然周维度。周结快照是客户端历史、后台查询、导出和争议对账的共同事实源；它不是一张只存最终金额的结果表，而是要能解释“哪一周、哪个公会、哪套政策、哪些输入、如何拆分、扣了什么、进了哪个余额池”。

| 快照组 | 至少保留的业务事实 | 用途 |
|---|---|---|
| 周期快照 | 自然周标识、周开始/结束、结算触发时点、业务时区 | 防止前后台错周；固定记录 UTC+3 及左闭右开的周区间 |
| 政策快照 | “自由政策（周结）”、政策版本、分成比、钻石换算美元比例、主播分成比例、公会长分成比例、金币工资拆分比例 0.2 | 历史不得读取当前政策重算 |
| 政策更改归属 | 更改前后政策、操作人、操作对象、操作时间、归属日期、对应月/周周期及当天流水和余额转归结果 | 更改当天的更改前数据也按新政策计算；与原归属核对，防止月结、周结重复统计 |
| 关系快照 | 主播、公会、公会长、身份、加入/离开关系及该周归属 | 支持离职历史和同周跨公会分单 |
| 钻石输入快照 | 起始钻石余额、最终钻石余额、兑换钻石、本期有效钻石流水、本期有效钻石余额、无效/冻结调整结果 | 解释工资基数与余额变化 |
| 主播工资快照 | 单个主播总薪资、金币工资、非金币工资、非金币余额 | 支持主播账与余额池对账 |
| 公会长工资快照 | 每个主播贡献的公会长分成、公会长本人主播工资项、公会长管理工资、金币/非金币拆分 | 管理工资不含本人主播工资；本人主播工资仅计入主播总薪资，避免双身份重复累计 |
| 公会汇总快照 | 主播工资总额、公会长管理工资总额、公会总薪资、公会总金币工资、公会总非金币工资、公会薪资余额 | 支持公会总账与成员分账勾稽 |
| 余额池结果 | 主播/公会长个人薪资余额、金币工资奖励余额、主播转入薪资余额的本次入账或承接关系 | 保证提现资产范围可追溯 |
| 处理状态 | 结算状态、快照版本及既有重试/补偿所需的业务标识 | 防止重复结算、重复入账 |

上述内容用于既有资金链和历史追溯，不代表全部需要显示在客户端页面。客户端只展示脑图明确继承的现有报表字段；后台和导出按现有字段范围承接，快照内部的计算中间结果不能因为页面未展示就丢失。

3. 离会/移除前先结算原公会归属期间的有效流水、有效余额和工资；结算成功、生成快照及余额池结果后清空已结算钻石余额，再解除原关系。未完成结算不得直接切断归属。
4. 新公会仅承接新归属期间产生的数据，不接管原公会工资和余额；离会后、加入新公会前的数据不得因后来入会倒挂给新公会。
5. 已结算原公会记录保留在该自然周历史中。周一结算仅处理尚未结算部分，不再次结算或入账已完成的离会记录。
6. 公会周报按各自归属时间段汇总，后台明细及导出保留归属快照；客户端同周历史与后台总额应能对应。结算后的个人余额仍归用户本人。
