# Lucky 子目录规则

## 查询与核验

处理幸运礼物的用户查询、金额核验、账务异常、RTP 或卡牌问题前，必须先阅读 `核心业务规则.md`，并按其中的“核验顺序”和“结论分级”输出。

- 用户输入纯数字时，继承项目根规则：按 `ln_user.user_no` 定位用户；仅用户明确说明是 `user_id` 时才按 `user_id` 查询。
- 先确认查询环境、时间范围、用户角色（送礼方/收礼方）和核验对象（单笔 `give_gift_id`、批次或区间）。信息缺失时，以可确认范围查询并在结论中声明边界。
- 数据证据顺序固定为：`ln_give_gift` -> `lucky_gift_draw_event` -> `ln_wallet_log` -> `lucky_gift_report_projection` -> 日汇总/卡牌记录。界面文案、动画和通知不能作为到账或统计证据。
- 查询结果必须先核对列名与前 3 行；任何空值、重复、金额不等、状态矛盾或快照缺失均单列 `异常声明`，不得用推测金额补齐。

## 结论口径

- 先给出结论分级：`正常`、`处理中`、`待投影` 或 `异常`；再列出关键证据、金额和下一步。
- 开奖结果与到账结果分开陈述：事件记录证明“抽到什么”，成功钱包流水证明“是否到账”，投影记录证明“是否进入统计”。
- 涉及 RTP 上限、非双边基础钻石归属或重复成功流水时，按 `核心业务规则.md` 的已确认口径核验并明确记录证据。
- 查询或对比 RTP 配置时，必须同时列出 MySQL `lucky_gift_rtp_config.id=1` 与 Redis `lucky_gift:config:rtp` 的实际值、逻辑库和 TTL；以 Redis 命中值作为运行时生效配置，缓存未命中时明确声明回源 MySQL。
- 仅在每个必需环节都有可追溯记录、金额等式成立且不存在异常声明时，才能判定为 `正常`。

## 文档维护

- 发现新的表字段、状态枚举、流水类型、可复现异常模式或已确认的实现变更时，更新 `核心业务规则.md` 中对应的单一条目。
- `核心业务规则.md` 是幸运礼物核验口径的唯一业务来源；本文件仅定义何时读取它和如何执行查询。
