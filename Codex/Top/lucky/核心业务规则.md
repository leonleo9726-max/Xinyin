# 幸运礼物核心业务规则

## 1. 用途与边界

本文件用于按用户、送礼记录或时间范围核验幸运礼物数据。核验结论只以数据库业务事实、成功钱包流水和已发布投影为依据，不以客户端动效、通知或页面展示为依据。当前业务不包含退款和冲正场景。

**输入最小集：** 用户号/用户 ID、时间范围，以及待核验对象（单笔 `give_gift_id`、连送批次或区间）。

**输出最小集：** 用户角色、业务结论、送礼金额、开奖金额、实际到账金额、统计状态，以及异常声明和下一步。

## 2. 数据证据链

| 环节 | 主数据 | 回答的问题 | 核验原则 |
| --- | --- | --- | --- |
| 送礼事实 | `ln_give_gift` | 是否发生有效幸运送礼、类型、份数、总价、送收双方是谁 | 一条记录是一笔聚合送礼；幸运类型为 35 或 36 |
| 逐份开奖 | `lucky_gift_draw_event` | 每一份抽到什么、使用何种玩法和受理价 | 一份礼物对应一条事件，`unit_index` 必须连续且唯一 |
| 钱包到账 | `ln_wallet_log` | 金币/钻石是否真正到账或扣除 | 只认 `status=1` 的成功流水 |
| 报表发布 | `lucky_gift_report_projection` | 该笔是否已计入最终投入产出 | 投影是统计幂等边界，不等同开奖或到账 |
| 汇总与权益 | `lucky_io_day_agg`、`lucky_user_mode_day_agg`、`lucky_daily_participant`、`lucky_card_grant_record` | RTP、参与人数、用户维度统计和卡牌判定 | 只能在事实、流水和投影核验后解释 |

**证据优先级：** `ln_give_gift` 确认业务身份，事件表确认开奖结果，钱包流水确认资产，投影确认统计。三类事实缺一不可，不能相互代替。

## 3. 标准核验顺序

### 3.1 定位范围

1. 以用户号定位 `ln_user`，明确该用户是送礼方、收礼方，或两种角色都有。
2. 在目标时间范围内定位 `ln_give_gift`，记录 `id`、`type`、`number`、`total_price`、送收双方、房间和受理时间。
3. 非 35/36 类型不属于幸运礼物；正常情况下不应产生幸运开奖事件或幸运奖励流水。

`ln_give_gift.add_time` 是 Unix 秒级时间戳。按自然日筛选时必须使用 `UNIX_TIMESTAMP(日期边界)`，不得将该整数字段直接与 `DATE` 或 `DATETIME` 比较。

### 3.2 判定是否成功受理

1. 找到该 `give_gift_id` 的成功扣币流水，金额必须为 `-total_price`。
2. 扣币失败或扣币状态未知时，不应有开奖、奖励或最终投影；结论为 `处理中`、`未受理` 或 `异常`，取决于是否存在相互矛盾的后续记录。
3. 已受理后礼物下架、改价、规则改版不改变该笔的类型、单价或概率版本。

### 3.3 核对逐份事件

每笔已受理的幸运送礼应满足：

```text
事件数 = ln_give_gift.number
unit_index = 1..number，连续且无重复
SUM(accepted_unit_price) = ln_give_gift.total_price
同一笔事件玩法一致
```

不满足任一条件时，停止“正常”判定，列为 `异常` 并保留缺失/重复事件 ID。

### 3.4 核对送礼方金币

逐份事件的开奖结果为：

```text
sender_coin_amount = FLOOR(accepted_unit_price * sender_multiplier)
sender_coin_amount > 0  => sender_result = WIN
sender_coin_amount = 0  => sender_result = MISS
```

- `WIN` 事件必须各有一笔等额、成功的金币奖励流水：`type=1`、`bus_type=10012`、`bus_id=draw_event_id`。
- `MISS` 事件不能有 `bus_type=10012` 奖励流水。
- 开奖已确定但奖励流水未成功时，结论只能是 `处理中` 或 `待补发`，不能按事件金额认定已到账。

### 3.5 核对收礼方钻石

| 玩法 | 事件口径 | 钱包核验 |
| --- | --- | --- |
| 非双边 | 只结算基础钻石：`FLOOR(number * accepted_unit_price * 0.1)` | 同一 `give_gift_id` 汇总后应有一笔成功钻石流水 |
| 双边 | 每份为 `FLOOR(accepted_unit_price * recipient_multiplier)`，先逐份取整再求和 | 成功钻石流水应等于 `SUM(recipient_diamond_amount)` |

钻石流水固定核验：`type=4`、`status=1`、`bus_type=40002`、`bus_id=give_gift_id`。金额为 0 时不应创建对应奖励流水。

## 4. 玩法判定规则

### 4.1 非双边幸运礼物

- 每份仅进行一次送礼方金币随机，奖池为 `SINGLE_SENDER_COIN`。
- 收礼方不进行幸运钻石随机，基础钻石不受送礼方中奖与倍率影响。
- 事件正常终态为 `NO_RECIPIENT_DRAW`。
- 基础钻石是独立来源，不计入送礼方返币或送礼方 RTP。

### 4.2 双边幸运礼物

1. 每份先进行送礼方金币随机，奖池为 `BILATERAL_SENDER_COIN`。
2. 送礼方 `WIN` 后，收礼方使用 `BILATERAL_RECIPIENT_A`；送礼方 `MISS` 后，使用 `BILATERAL_RECIPIENT_B`。
3. A/B 是收礼方奖池路由，不代表收礼方一定中奖。送礼方与收礼方可同时中奖。
4. 收礼方开奖后，事件终态为 `RECIPIENT_DRAWN`。

双边额外幸运钻石与平台成本：

```text
baseline_i = FLOOR(accepted_unit_price_i * 0.1)
extra_lucky_diamond_i = MAX(recipient_diamond_amount_i - baseline_i, 0)
receiver_lucky_diamond = SUM(extra_lucky_diamond_i)
receiver_lucky_coin_equiv = FLOOR(receiver_lucky_diamond / 5)
```

平台 RTP 的双边钻石成本按批次/统计范围先汇总额外幸运钻石，再按 `5` 钻石折 `1` 金币统一向下取整；不得逐份折算后求和。

## 5. 投影、RTP 与卡牌

### 5.1 投影发布条件

`lucky_gift_report_projection` 只有在以下事实同时成立时才应发布：

1. 主单类型为 35 或 36，事件数、序号、玩法和受理金额全部一致。
2. 存在一笔等额成功扣币流水。
3. 每个中奖事件各有一笔等额成功金币奖励，未中奖事件无金币奖励。
4. `ln_give_gift.guild_income_status = 2`。
5. 双边钻石大于 0 时，存在一笔等额成功钻石流水。
6. 未被 RTP 上限逻辑永久排除。

满足开奖与到账但尚未发布投影时，结论为 `待投影`，不能计入最终 RTP。

### 5.2 RTP 统计口径

```text
总盘 RTP = (送礼方有效返币 + 双边额外幸运钻石等价金币成本) / 全部有效投入
非双边 RTP = 非双边送礼方有效返币 / 非双边有效投入
双边送礼方 RTP = 双边送礼方有效返币 / 双边有效投入
双边平台 RTP = (双边送礼方有效返币 + 双边额外钻石等价金币成本) / 双边有效投入
```

- 当前无退款或冲正：有效投入为成功扣币金额，送礼方有效产出为成功金币奖励金额；不做回滚或净值重算。
- 比率先汇总分子与分母再相除；跨日参与用户按 `user_id` 去重，不能累计每日人数。
- 卡牌成本不计入任一 RTP 指标。

### 5.3 幸运卡牌核验

- 只有投影已发布、`report_eligible=1` 且非 RTP 上限排除的事件才进入发卡判定。
- 卡牌资格按玩法隔离读取有效投入、实际 RTP、体验亏损和连续未中奖；双边与非双边不能互相借用历史。
- 读取 `lucky_card_grant_record` 的历史快照解释结果，不能按当前配置反推或覆盖既有判定。
- `decision=GRANTED` 时应为 `reason=ELIGIBLE`、`card_delta=1`；拒绝时 `card_delta=0`，以首个命中的拒绝原因解释。


### 5.4 概率配置与 Redis

- **MySQL 是配置主源。**`lucky_gift_draw_rule` 和 `lucky_gift_rtp_config` 采用 Redis 优先、MySQL 回源的读取方式；缓存不设置 TTL。只修改 MySQL 不会使已缓存的开奖或 RTP 配置自动生效。
- **幸运卡配置不走 Redis 配置缓存。**`lucky_card_trigger_config` 在每次发卡判定时直接读取当前玩法最新的 `enabled=1` 配置；`lucky_card_reward_config` 在每次抽卡时直接读取 `enabled=1 AND probability>0` 的奖品配置。
- **抽卡概率口径。**启用奖品的 `probability` 总和必须精确等于 `1.0000000000`；随机权重为 `probability * 10^10`，命中概率为该权重除以启用权重总和。十连抽是 10 次独立、有放回随机。
- **历史结果不回算。**`lucky_card_draw_item` 固化命中配置、`probability_snapshot`、随机值和权重区间；后续修改奖品概率不能覆盖或用于重算既有抽卡结果。
- **配置变更顺序。**对开奖规则或 RTP 配置：先提交 MySQL 事务，再删除受影响 Redis 配置键，随后用业务请求回源重建并核对 Redis 与 MySQL 一致。禁止先删缓存再提交事务；修改 RTP 上限时删除整个 RTP Hash，不应只处理单个字段。
- **卡牌 Redis 仅为运行时状态。**用户级发卡锁、按玩法的未中奖净计数和抽奖令牌不属于配置缓存。修改 `lucky_card_trigger_config` 或 `lucky_card_reward_config` 时不得删除这些状态键；删除计数会触发数据库快照恢复，删除有效令牌会使未完成抽奖令牌过期。
- **环境边界。**Redis 操作先查询逻辑库 `7`（默认库）和 `10`（主要库），确认目标 key 所在库后才能读取、清理或变更；两个库均未命中或同时命中时先声明结果并等待确认。任何查询、清理或核验操作均以目标环境的最终生效配置为准。
### 5.5 开奖概率调整操作

适用于调整送礼方返币或双边收礼方返钻的总中奖率。概率只由同一 `play_type + reward_pool` 内满足 `status='ACTIVE' AND enabled=1 AND weight>0` 的规则决定，`config_code` 当前不参与筛选。

1. **确认范围与快照。**先确认测试环境，执行 `SHOW COLUMNS FROM lucky_gift_draw_rule`；按玩法和奖池导出全部生效规则、配置缓存键和变更前权重到 `outputs`。不得仅查看部分规则或按 `config_code` 推断生效范围。
2. **确认中奖与未中奖规则。**`multiplier>0` 是中奖规则，`multiplier=0` 是未中奖规则。若生效池没有未中奖规则，现状中奖率为 100%；调整为低于 100% 的目标时必须新增或启用未中奖规则，不能只降低中奖规则权重。
3. **计算权重。**目标中奖率为 `r` 时，应满足 `SUM(weight where multiplier>0) / SUM(weight) = r`。保留中奖倍率相对分布；权重为整数，需选择能精确满足比例的整数总权重。当前中奖规则权重相等时，可令每条中奖规则权重为 `W`，未中奖规则权重为 `N * W * (1-r) / r`，其中 `N` 为中奖规则数。
4. **显式写全新规则字段。**新增未中奖规则必须显式指定 `config_code`、玩法、奖池、`status`、`multiplier`、`weight`、`enabled` 以及公屏、飘屏、动画、跑马灯、震动和资源 URL 字段；不要依赖数据库默认值。未中奖展示是否关闭需先按产品口径确认。
5. **MySQL 事务。**锁定目标生效规则后校验奖池存在、配置编码没有混杂、未中奖规则状态符合预期；在同一事务内更新权重和新增/启用未中奖规则，提交失败必须回滚。不得修改历史 `lucky_gift_draw_event` 或已完成的钱包、投影记录。
6. **Redis 同步。**数据库事务提交后，先按 DB7、DB10 顺序查询受影响的 `lucky_gift:config:*` 缓存键；仅在确认命中的逻辑库删除。两个库均未命中时记录“无缓存可清理”，两个库同时命中时停止并等待确认；无需人为创建或删除其他业务状态键。
7. **回查与归档。**重新按奖池汇总中奖权重、未中奖权重、总权重和生效规则数，验证目标比例精确成立；导出变更后结果到 `outputs`，并保留变更前快照。发现目标奖池缺失、规则版本混杂、比例无法由整数权重精确表达或 Redis 访问失败时，停止并按异常处理。

## 6. 结论分级与输出

| 结论 | 必备事实 | 输出重点 |
| --- | --- | --- |
| 正常 | 主单、逐份事件、扣币/奖励流水和投影均完整，金额等式成立 | 玩法、投入、返币/返钻、投影时间 |
| 处理中 | 扣币、开奖或发奖尚未到终态，但没有冲突事实 | 当前阶段、已有事件 ID、等待的流水或消息 |
| 待投影 | 开奖和到账均正确，但投影未发布 | 缺少的投影条件、是否影响 RTP/卡牌 |
| 异常 | 缺事件、重复流水、金额不等、终态冲突或快照缺失 | 异常声明、受影响 ID、不可下结论的字段 |

建议输出顺序：**结论** -> **查询范围** -> **关键金额与等式** -> **证据 ID/状态** -> **异常声明** -> **下一步**。

## 7. 已确认的特殊核验规则

1. **RTP 上限。**以最近 30 个自然日 `lucky_io_day_agg` 与 `lucky_gift_rtp_config` 的比较结果为准。达到上限后，该批次仍按已受理流程结算：送礼方金币固定为 0、`sender_result=MISS`，收礼方按 10% 基准钻石结算，`recipient_pool=RTP_LIMIT_BASE`。投影应为 `projection_state=2`、`exclusion_reason=RTP_LIMITED`，不进入投入产出汇总与卡牌判定。核验时应看到已扣币和基准钻石结算，不能将其误判为未受理。
2. **非双边基础钻石归属。**批次总额为 `FLOOR(number * accepted_unit_price * 0.1)`。当前实现将总额写入该 `give_gift_id` 的第一条 `lucky_gift_draw_event.base_recipient_diamond_amount`，其余逐份事件为 0；收礼钱包按 `give_gift_id` 汇总入账。核验单笔事件时，首条金额不代表单份分配，须以批次总额和成功钻石流水判断。
3. **退款与冲正。**当前无退款、冲正业务场景；核验范围只包括正常成功扣币、开奖、发奖和投影链路。发现相关流水或状态时，应按 `异常` 处理并保留证据。
4. **重复成功流水。**同一业务身份出现多笔成功金币或钻石流水时，必须判定为 `异常`。核验业务身份时，金币按 `bus_type=10012 + draw_event_id`，钻石按 `bus_type=40002 + give_gift_id`；同时确认数据库是否具备覆盖该身份的唯一约束。
5. **投影与汇总数据保留。**不得手动清理 `lucky_gift_report_projection`、`lucky_io_day_agg` 或 `lucky_user_mode_day_agg` 的历史记录。清理会使仍存在的主单、开奖和钱包流水无法进入 RTP 统计，当前聚合值仅代表残留投影，不能作为完整历史 RTP 结论。发生误清理后，应从备份恢复或按原始事实与成功流水重建投影及汇总，再重新核验。
