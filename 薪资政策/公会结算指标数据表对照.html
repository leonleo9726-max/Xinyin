App 公会结算 Data Center — 页面指标核对手册

这份文档帮你搞清楚一件事：App Data Center 页面上的每个数字，是从数据库哪些表、哪些字段算出来的。
当页面数字看起来不对时，按文档里的 SQL 去查数据库，就能定位问题出在哪一步。
结算周期：每月分两半 — 1~15 日是一个周期，16~月底是一个周期。例如今天 6/12，当前周期 = 6/1~6/15。
2026-06-12 更新：修正可借支双重扣减 Bug 后，第 18/19/22/23/24/25 项算法已按 PRD 调整（借支结算后清零、历史欠款取最新归档、可借支直接读字段），并修正了文档中的表名（app_user_agency）和单位（公会表 borrowed_amount 为美元）。

主播登录 → 只查自己一个人的数据 → "公会"开头的字段 = 自己的值

公会长登录 → 查全公会所有人的数据 → "公会"开头的字段 = 真正的全员合计

数据从哪来？

查当前周期（如 6/1~6/15）
app_user_account（实时余额） + 薪资配置 → 内存实时计算 每次打开页面时，用账户里的实时钻石余额 + 薪资档位配置，现场算出工资

查历史周期（如 5/16~5/31）
结算记录表 app_payer_host_salary_detail_v2 — 只看 status=2（已打款）的记录求和

涉及的数据库表

表名通俗说明什么时候用
app_user_account用户的钱包 — 钻石余额、预支余额、可提现余额都在这。当前周期的工资就是用这里的实时钻石余额现场算出来的查余额类指标 + 当前周期工资计算的输入
app_payer_host_salary_detail_v2历史结算记录 — 每次结算打款后生成一条查历史周期的工资 + 已结算钻石
app_payer_host_salary_config_v2薪资档位配置 — 钻石达到多少对应什么等级和工资查 Diamond salary level
app_payer_diamond_purchase_detail钻石兑换金币的记录 — 主播把钻石换成金币时记一条，spent_diamonds = 花掉的钻石数算 Current Diamond target 的一部分（兑换花掉的钻石也算流水）
app_live_user_site_daily_summary每天直播了多久的汇总查 Effective days
app_user_agency公会信息 — 借支额度 borrowable_amount、已借金额 borrowed_amount（两个字段单位都是美元，不是分）。借支审批通过时额度原子扣减、结算还款时加回，是滚动余额不是固定授信查借支相关指标
app_payer_agency_owner_surplus公会长盈余归档表 — 每次结算（双周/手动）归档一条本期账目快照，欠款靠它跨周期传导查历史欠款 + 盈余详情列表
admin_content_agency_borrow_salary_log借支/预支流水日志 — type: 1=借支 2=预支 3=借支还款 4=预支还款（金额单位美元）算本期借支 + 借支/预支记录页
下面 SQL 里的占位符：?uid 换成用户 ID，?aid 换成公会 ID，?start / ?end 换成周期起止时间（如 '2026-06-01' / '2026-06-15'）

主播视角 — Data Center 页面指标（1~11 项）

1. Current Diamond target（本期钻石流水） 主播+公会长 master 不变
一句话：这个主播在本结算周期里，一共经手过多少钻石。
账户表
gain_diamond + send_gain_diamond + 结算记录表
SUM(diamonds) 已打款 + 兑换记录表
SUM(spent_diamonds)
钻石换金币花掉的 = 页面显示值
当前余额 + 已被结算扣走的 + 兑换花掉的 = 本周期真实钻石流水
为什么要加三张表？因为结算打款时会清零钻石余额。比如赚了 2000 万，结算扣走 1800 万，余额只剩 200 万。 只看余额会误判档位，所以要把三部分加起来。
在数据库里找不到这个值 — 它不存在于任何单表，是查出三个数加起来的。
-- ① 当前钻石余额（账户表） SELECT gain_diamond + send_gain_diamond AS 当前余额 FROM app_user_account WHERE user_id = ?uid; -- ② 本周期已结算钻石（结算记录表） SELECT IFNULL(SUM(diamonds), 0) AS 已结算钻石 FROM app_payer_host_salary_detail_v2 WHERE user_id = ?uid AND status = 2 AND settlement_time BETWEEN ?start AND ?end; -- ③ 本周期兑换金币花掉的钻石（钻石→金币兑换记录表） -- 主播把钻石换成金币时才会产生记录，没换过就是 0 SELECT IFNULL(SUM(spent_diamonds), 0) AS 兑换花掉的钻石 FROM app_payer_diamond_purchase_detail WHERE user_id = ?uid AND create_time BETWEEN ?start AND ?end; -- 页面值 = 当前余额 + 已结算钻石 + 兑换花掉的钻石
2. Diamond Balance（当前钻石余额） 主播+公会长 master 不变
一句话：主播账户里现在有多少钻石。注意是两个字段加起来，不是某一个。
app_user_account 表：gain_diamond（收礼赚的）+ send_gain_diamond（后台赠送的）
SELECT gain_diamond + send_gain_diamond AS 钻石余额 FROM app_user_account WHERE user_id = ?uid;
3. Current Host Salary（主播档位工资） 主播+公会长 master 不变
一句话：根据钻石量匹配的档位工资 + 超出部分的额外工资。不含 TG 奖励（TG 在第 4 项单独显示）。
算法 = 薪资配置表的 host_salary（档位基础工资）+ 超出部分（(钻石 - 档位阈值) ÷ excessDiamondsRate）

当前周期 → 用 app_user_account 的实时钻石余额匹配 app_payer_host_salary_config_v2 档位，现场计算
历史周期 → 结算记录表的 SUM((host_salary + excess_diamonds_salary) × salary_ratio)
 注意：表里 host_salary 只存了档位基础工资，excess 和 ratio 都是独立字段，要手动组合计算
detail_v2 表存的是原始值，页面显示的是聚合后的值，两者不能直接对比！

数据库里的字段（都是乘比例之前的原始值）：
• host_salary = 档位基础工资（和 config_v2 表配的一样）
• excess_diamonds_salary = 超出档位的额外工资
• host_tg_reward = TG 奖励
• salary_ratio = 发放比例（1.00 或 0.70）
• actual_salary = (host_salary + excess + tg) × ratio = 总工资（这个是算好的）

页面的 Current Host Salary = (host_salary + excess_diamonds_salary) × salary_ratio
代码在读出来后做了合并和乘比例（SalaryAggregationCalculator），不是直接读某个字段。
-- 当前周期：工资是实时算的，不存在某张表里 -- 验证方式：查钻石余额 → 对照薪资配置表的档位 → 看 host_salary 金额是否匹配 SELECT gain_diamond + send_gain_diamond AS 钻石余额 FROM app_user_account WHERE user_id = ?uid; SELECT level, diamonds, host_salary, host_tg_reward FROM app_payer_host_salary_config_v2 WHERE diamonds <= {上面查到的钻石余额} ORDER BY diamonds DESC LIMIT 1; -- 历史周期（结算记录表） -- 注意：页面值 = (host_salary + excess) × ratio，不是直接 SUM 某个字段 SELECT SUM((host_salary + IFNULL(excess_diamonds_salary, 0)) * salary_ratio) AS 页面主播工资, -- 拆开看各部分： SUM(host_salary) AS 档位工资原始值, SUM(IFNULL(excess_diamonds_salary, 0)) AS 超出工资原始值, salary_ratio AS 发放比例 FROM app_payer_host_salary_detail_v2 WHERE user_id = ?uid AND status = 2 AND settlement_time BETWEEN ?start AND ?end;
4. Current TG Reward（TG 奖励） 主播+公会长 master 不变
一句话：TG 渠道拉新的额外奖励金额。数据来源和第 3 项一样（当前周期实时算 / 历史查结算记录表）。
-- 当前周期：同第 3 项，用钻石余额匹配薪资配置表的 host_tg_reward，再乘 salary_ratio -- 历史周期（注意也要乘比例！） SELECT SUM(host_tg_reward * salary_ratio) AS 页面TG奖励 FROM app_payer_host_salary_detail_v2 WHERE user_id = ?uid AND status = 2 AND settlement_time BETWEEN ?start AND ?end;
5. Current Host Total salary（主播实际总工资） 主播+公会长 master 不变
一句话：主播最终能拿到的总金额。当前周期是每次打开页面时实时计算，不从某张表直接读。
app_user_account
钻石余额 → 匹配薪资配置档位 → (host_salary + excess_salary + host_tg_reward) × salary_ratio = 页面值
（档位工资 + 超出薪资 + TG） × 发放比例 = 实际到手

发放比例：有效天 ≥ 6 天 且 总时长 ≥ 12 小时 → 100%，否则 → 70%（首周期保护不打折）
-- 当前周期：验证步骤 -- 1) 查钻石余额 SELECT gain_diamond + send_gain_diamond AS 钻石余额 FROM app_user_account WHERE user_id = ?uid; -- 2) 匹配薪资档位，看 host_salary / host_tg_reward 对不对 SELECT level, diamonds, host_salary, host_tg_reward FROM app_payer_host_salary_config_v2 WHERE diamonds <= {钻石余额} ORDER BY diamonds DESC LIMIT 1; -- 3) 查有效天数和时长，判断发放比例是 100% 还是 70% SELECT COUNT(*) AS 有效天 FROM app_live_user_site_daily_summary WHERE user_id = ?uid AND dates BETWEEN ?start AND ?end AND duration >= 7200; -- 4) 手动验算：(host_salary + excess + tg_reward) × ratio = 页面总工资 -- 历史周期（直接查结算记录表） SELECT SUM(actual_salary) FROM app_payer_host_salary_detail_v2 WHERE user_id = ?uid AND status = 2 AND settlement_time BETWEEN ?start AND ?end;
补充：salary_ratio（发放比例）是怎么来的？ 影响第 3/4/5 项 master 不变
一句话：主播每个周期的工资会根据直播达标情况打折 — 达标了拿 100%，没达标只拿 70%。第 3/4/5 项的值都受这个比例影响。
判定规则（按优先级）：

① 首个周期保护 — 加入公会后的第一个结算周期，不管有没有达标，一律 1.00（100%）
 判断方式：app_agency_member.join_time 在当前周期的 startTime 之后 → 是首周期

② 达标 — 有效天数 ≥ 6 天 并且 总上麦时长 ≥ 12 小时 → 1.00（100%）

③ 未达标 — 不满足上面任何一条 → 0.70（70%，扣 30%）
数据从哪来：
有效天数 = app_live_user_site_daily_summary 中 duration ≥ 7200（2小时）的记录数
总上麦时长 = 同表所有记录的 SUM(duration) / 3600（秒转小时）
是否首周期 = app_agency_member.join_time 是否在 ?start 之后
-- 查有效天数和总时长 SELECT COUNT(CASE WHEN duration >= 7200 THEN 1 END) AS 有效天数, ROUND(SUM(duration) / 3600, 2) AS 总上麦小时 FROM app_live_user_site_daily_summary WHERE user_id = ?uid AND dates BETWEEN ?start AND ?end; -- 有效天数 >= 6 且 总上麦小时 >= 12 → ratio = 1.00，否则 = 0.70 -- 查是否首周期（加入时间在当前周期之后 = 首周期，ratio 固定 1.00） SELECT join_time FROM app_agency_member WHERE user_id = ?uid AND status = 1; -- 如果 join_time > ?start → 首周期保护，ratio = 1.00，不受有效天数影响 -- 历史周期可以直接查 detail_v2 表里存好的 salary_ratio SELECT salary_ratio FROM app_payer_host_salary_detail_v2 WHERE user_id = ?uid AND status = 2 AND settlement_time BETWEEN ?start AND ?end;
6. Diamond salary level（薪资等级） 主播+公会长 master 不变
一句话：根据 Diamond Balance（第 2 项）去配置表匹配的等级。钻石越多等级越高。
SELECT level, diamonds, host_salary, host_tg_reward FROM app_payer_host_salary_config_v2 WHERE diamonds <= ( SELECT gain_diamond + send_gain_diamond FROM app_user_account WHERE user_id = ?uid ) ORDER BY diamonds DESC LIMIT 1;
7. Effective days（有效天数） 主播+公会长 master 不变
一句话：周期内每天直播满 2 小时算 1 天。不到 2 小时的不算。不在薪资表里，在直播时长汇总表中。
-- 有效天数 SELECT COUNT(*) AS 有效天数 FROM app_live_user_site_daily_summary WHERE user_id = ?uid AND dates BETWEEN ?start AND ?end AND duration >= 7200; -- 7200秒 = 2小时 -- 查每天明细（看哪天没达标） SELECT dates AS 日期, ROUND(duration/3600, 2) AS 小时 FROM app_live_user_site_daily_summary WHERE user_id = ?uid AND dates BETWEEN ?start AND ?end ORDER BY dates;
8. Host Advance Salary（已预支金额） 主播+公会长 master 不变
一句话：主播提前预支了多少工资（还没结算就先拿走的钱）。
当前周期 → app_user_account.advance_salary_total_amount（美元）
历史周期 → 结算记录表 SUM(advanced_amount) ÷ 100（注意：这个字段存的是「分」，除以 100 转美元！）
-- 当前周期（账户表，单位已经是美元） SELECT advance_salary_total_amount AS 已预支 FROM app_user_account WHERE user_id = ?uid; -- 历史周期（结算记录表，注意除以 100！） SELECT IFNULL(SUM(advanced_amount), 0) / 100 AS 已预支 FROM app_payer_host_salary_detail_v2 WHERE user_id = ?uid AND status = 2 AND settlement_time BETWEEN ?start AND ?end;
9. Current Salary balance（工资余额） 主播+公会长 master 不变
一句话：总工资减掉已预支 = 还剩多少。用第 5 项减第 8 项验证即可。
= 第 5 项（总工资） − 第 8 项（已预支）
10. Agent shared salary（分给公会长的佣金） 主播+公会长 master 不变
一句话：这个主播给公会长贡献了多少佣金 = 公会长提成 + 公会长 TG 奖励。
当前周期 → 和工资一样实时计算（用钻石余额 + 配置），不从表直接读
历史周期 → 结算记录表的 SUM(agency_owner_salary) + SUM(agency_owner_tg_reward)
-- 当前周期：实时计算，验证方式同第 3 项（钻石余额 → 匹配配置 → 看佣金） -- 历史周期 SELECT IFNULL(SUM(agency_owner_salary),0) + IFNULL(SUM(agency_owner_tg_reward),0) AS 公会长佣金 FROM app_payer_host_salary_detail_v2 WHERE user_id = ?uid AND status = 2 AND settlement_time BETWEEN ?start AND ?end;
11. 钱包可提现金额 主播+公会长 master 不变
一句话：以前结算打过的钱里，还没提走的有多少。跟选哪个周期没关系，永远是账户实时值。
app_user_account.withdrawal_balance（美元）
SELECT withdrawal_balance AS 可提现 FROM app_user_account WHERE user_id = ?uid;

公会长额外视角 — 公会级汇总 + 公会长专属（12~25 项）

以下指标只有公会长和管理员能看到完整数据。汇总类 = 把全公会每个人的对应指标加起来。
-- 先查公会所有成员 SELECT user_id, role FROM app_agency_member WHERE agency_id = ?aid AND status = 1;
12. 公会钻石流水 / 公会钻石余额 公会长 master 不变
一句话：全员的第 1 项加起来 / 全员的第 2 项加起来。
13. 公会主播薪资 / 公会主播 TG 公会长 master 不变
一句话：全公会所有主播的总工资之和 / TG 奖励之和。
公会主播薪资 = 全员 SUM(actual_salary)
 actual_salary = (档位工资 + 超出工资 + TG) × 发放比例 = 第 5 项，已经包含了 TG 和发放比例

公会主播 TG = 全员 SUM(host_tg_reward × salary_ratio)
 这个数只是让公会长看 TG 占了多少，不会在第 15 项公会总工资里再加一次（actual_salary 里已经含了）
-- 历史周期 -- actual_salary = (host_salary + excess + tg_reward) × ratio，已包含所有部分 SELECT SUM(actual_salary) AS 公会主播薪资_含TG含比例, SUM(host_tg_reward * salary_ratio) AS 公会主播TG_仅展示用 FROM app_payer_host_salary_detail_v2 WHERE agency_id = ?aid AND status = 2 AND settlement_time BETWEEN ?start AND ?end; -- 当前周期：每个成员实时算的，需逐人查钻石余额 → 匹配档位 → 算 actual_salary → 全员求和
14. 公会长佣金 公会长 master 不变
一句话：全员的第 10 项加起来 = 公会长管理所有主播获得的总佣金。
-- 当前周期：实时计算，无法直接查表 -- 历史周期 SELECT SUM(agency_owner_salary) + SUM(agency_owner_tg_reward) AS 佣金 FROM app_payer_host_salary_detail_v2 WHERE agency_id = ?aid AND status = 2 AND settlement_time BETWEEN ?start AND ?end;
15. 公会总工资 公会长 master 不变
一句话：= 第 13 项（全员主播薪资）+ 第 14 项（公会长佣金）。
16. 公会已预支 公会长 master 不变
一句话：全员的第 8 项（已预支）加起来。
17. 公会工资余额 公会长 CHANGED 算法变更
一句话：公会总工资扣掉已预支后还剩多少。
master：总工资 − 已预支 − 已借支（可能出现负数）
refact：总工资 − 已预支（不再减借支，最低 0）
为什么改：旧版把借支也扣进来，导致余额可能为负。新版认为借支是独立的债务关系，不应扣。
18. 公会已借支（Agent borrowed amount） 公会长 CHANGED 06-12 调整
一句话：本期内、最后一次结算之后新借的钱。结算会把之前的借支处理掉（能还的从工资扣、还不完的转历史欠款），所以结算后这个字段清零，之后再借才重新累计。
旧口径：app_user_agency.borrowed_amount 字段（累计未还，结算后未还清不清零）
新口径：本期借支日志中、晚于本期最后一次结算时间的 type=1 记录之和（结算后清零，未还部分体现在第 25 项历史欠款）
-- ① 先查公会长本期最后一次结算时间（没有结算记录则不过滤） SELECT MAX(settlement_time) FROM app_payer_host_salary_detail_v2 WHERE user_id = ?owner_uid AND agency_id = ?aid AND status = 2 AND settlement_time BETWEEN ?start AND ?end; -- ② 统计该时间之后的本期借支（type=1，金额单位美元） SELECT IFNULL(SUM(salary_amount), 0) AS 本期借支 FROM admin_content_agency_borrow_salary_log WHERE agency_id = ?aid AND to_user_id = ?owner_uid AND type = 1 AND create_time BETWEEN ?start AND ?end AND create_time > {①查到的时间，查不到用 '1970-01-01'}; -- 参考：当前未还借支余额（字段值，美元，不是页面口径但排查欠款时有用） SELECT borrowed_amount AS 未还借支美元 FROM app_user_agency WHERE agency_id = ?aid;
19. 公会可借支（Agent borrowable amount） 公会长 CHANGED 06-12 修复双扣
一句话：公会长还能再借多少钱 = 直接读字段。字段是滚动余额：借支审批通过时已原子扣减、结算还款时加回，未还借支留在 borrowed_amount 持续占用额度 — 字段值天然等于 PRD 公式「总额度 − 本期借支 − 历史欠款」。
06-09 版：字段 − 本期借支 − 历史欠款 — 字段本身已被借支扣过，等于又扣一遍（借 100 页面少 200 的 Bug 根源）
06-12 版：直接读 app_user_agency.borrowable_amount（美元），不再做任何动态扣减
SELECT borrowable_amount AS 页面可借支美元, borrowed_amount AS 未还借支美元, borrowable_amount + borrowed_amount AS 总授信额度 FROM app_user_agency WHERE agency_id = ?aid; -- 验证恒等式：borrowable + borrowed ≡ 总额度（借支/还款都不破坏这个和，只有 Admin 手动改额度才变）
20. 公会长总工资 公会长 master 不变
一句话：= 管理佣金（第 14 项）+ 自己作为主播的工资和 TG。公会长也能直播赚钱。
21. 公会长工资余额 公会长 CHANGED 算法变更
一句话：公会长的总工资减掉已预支。
master：总工资 − 预支 − 借支
refact：总工资 − 预支（不再减借支）
22. 本期薪资 公会长 NEW 06-12 调整
一句话：公会长本期未结算的实时收入 = 公会长总工资（佣金 + 作为主播的工资和 TG）− 本期预支。结算后实时部分转为已结算，这个字段自然清零，之后新产生的薪资重新累计。只有公会长自己能看。
My Agency 页面 = 第 20 项（公会长总工资，未结算实时口径）− 公会长本期预支
Data Center 页面 = 我的收入卡片 totalSalary − 当前预支余额（app_user_account.advance_salary_total_amount）
23. 本期借支 公会长 NEW 06-12 调整
一句话：与第 18 项完全同口径同值（PRD 要求两处统一）：本期内最后一次结算之后的借支，结算后清零。查询 SQL 见第 18 项。
24. 本期实际工资 公会长 NEW 06-12 调整
一句话：= 本期薪资（第 22 项）− 本期借支（第 23 项）− 历史欠款（第 25 项）。借多了或背着旧债时会显示负数。结算后薪资/借支清零：没有欠款时显示 0，有欠款时显示 −欠款（直观表达还欠多少）。
25. 历史欠款 公会长 NEW 06-12 调整
一句话：公会长到目前为止还欠平台多少钱没还清。页面展示取最新一条归档记录（含本期期中手动结算的归档），期中结算产生的欠款当场就会显示在这里，不用等到下个周期。
算法：取该公会最新一条盈余归档记录，看它的「本期实际工资」是否为负数：

• 实际工资 < 0（借支 + 旧债超过了工资）→ 历史欠款 = 实际工资的绝对值
• 实际工资 ≥ 0（工资覆盖了借支和旧债）→ 历史欠款 = 0

举个例子：
公会长工资 $200，但借了 $350 → 结算时归档 实际工资 = 200 - 350 = -$150
→ 结算后页面立即显示历史欠款 = $150（同时第 18/23 项本期借支清零）
这 $150 留在 app_user_agency.borrowed_amount 里持续占用借支额度，下次结算继续从工资里扣，扣清后归档转正、欠款归零
数据来源：app_payer_agency_owner_surplus 表 — 每次结算（双周 Job / 手动自由结算）归档一条记录，同周期多次结算时最新一条覆盖生效
两套口径注意：页面展示取「最新一条归档」（期中欠款即刻可见）；而结算时计算下期欠款传导取的是「本周期之前的最新归档」（避免同周期多次结算重复扣）
-- 页面展示口径：最新一条归档（含本期期中结算） SELECT cycle_start, cycle_end, period_salary, period_borrow, period_actual_salary, settlement_type, CASE WHEN period_actual_salary < 0 THEN ABS(period_actual_salary) ELSE 0 END AS 历史欠款 FROM app_payer_agency_owner_surplus WHERE agency_id = ?aid AND status = 1 ORDER BY cycle_end DESC, id DESC LIMIT 1; -- 如果一条归档都没有（从未结算过）→ 历史欠款 = 0 -- 盈余详情页（/surplusDetails）= 这张表按时间倒序分页，接口 GET /agency/salary/v2/owner-surplus/list

常见疑问

Q1: 页面值和数据库对不上，怎么排查？
三步走：① 当前周期的工资是实时算的 — 查 app_user_account 的钻石余额 + 薪资配置表对照；历史周期查结算记录表 ② 检查单位（分 vs 美元）③ 确认查的时间范围和周期对得上。
Q2: 怎么判断 Bug 是 master 还是 refact 引入的？
看标签。master 不变 有问题 → 线上也有。CHANGED / NEW 有问题 → refact 引入。
Q3: refact 到底改了什么？
工资余额不再减去借支。另外新增了 4 个公会长专属指标来单独展示借支和欠款。
06-12 又修了三处：① 可借支（第 19 项）从「字段再减借支/欠款」改回直接读字段 — 修复借 100 显示少 200 的双扣 Bug；② 借支金额（第 18/23 项）改为「最后一次结算之后的借支」，结算后清零；③ 历史欠款（第 25 项）改取最新归档，期中结算欠款当场可见。
Q8: 借支了 100，可借支为什么只少 100 不少 200？
因为 app_user_agency.borrowable_amount 是滚动余额：借支审批通过那一刻 DAO 已经原子扣了 100（带 WHERE borrowable_amount >= 100 防超借），页面直接读字段就是正确剩余额度。任何在字段基础上再减「本期借支/历史欠款」的算法都是双重扣减（06-09~06-12 期间的 Bug 形态）。
Q9: 结算后「本期借支」清零了，欠的钱去哪了？
两本账同时记：① 实际占额留在 app_user_agency.borrowed_amount（额度不恢复，下次结算继续从工资扣）；② 展示转到第 25 项「历史欠款」（取最新归档的负实际工资）。两边金额一致，还清后同时归零。
Q4: Current Diamond target 为什么在单表里找不到？
它是 3 张表的数据加起来的（钻石余额 + 已结算钻石 + 兑换金币花掉的钻石），不直接存储。用第 1 项的 SQL 分步查再相加。
Q5: 可提现金额为什么不随周期变化？
直接读账户余额，代表「以前结算打过来但还没提走的钱」，跟查询周期无关。
Q6: 主播和公会长看到的数字为什么不一样？
主播只查自己 → "公会"字段 = 自己的值。公会长查全员 → 真正的全公会合计。
Q7: App 端的工资会不会有延迟？
App 端每次打开页面都是实时计算的（读 app_user_account 的实时钻石余额 → 套公式），所以没有延迟。
注意：Admin 后台的薪资列表用的是另一张 app_payer_host_salary_realtime_snapshot 快照表（每 10 分钟刷新），两边机制不同。
